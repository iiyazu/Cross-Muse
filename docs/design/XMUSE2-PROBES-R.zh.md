# xmuse 2 信息协作层：真实工作流探针（R 系列，2026-10-12，r7）

**状态**：用户 10-12 提出。tick 世界的 S 系列有效果，但还不够：节奏、什么时候该同步、谁需要知道什么，都由脚本安排好了，测到的主要是"送达"。R 系列保留"小、确定、程序判定"，把场景换成真实的协作流程：没有 tick，agent 真写代码，信息层要由 agent 主动用起来。交给 base 实现，在 S 系列已排的第一批之后运行。授权和顺序见 `docs/HANDOFF-BASE.zh.md` 第 13 节。

## 0. 原则

1. **没有 tick，节奏由事件驱动。** 用户提需求，agent 自己干活、汇报、交接。脚本的刺激由可观察的事件触发（某成员第一次 `xmuse_done` 之后、某个文件出现之后、房间安静下来之后），不按固定时刻。房间安静（没有在跑的回合、没有排队的唤醒，持续 30 秒）或超过总时限（默认 20 分钟）就结束。
2. **真写代码，用隐藏验收测试判定。** 每个场景配一个很小的合成项目（3–6 个 Python 文件，只用标准库，测试用 `unittest`），带可见测试，agent 可以自己跑。验收测试不进工作区，判定时把工作区复制一份，再放进去跑。
3. **用户只做真实用户会做的事。** 提需求、中途改主意、回答被问到的问题、偶尔在侧栏插一句。不替 agent 转发（P-relay 组除外，它模拟的就是"手动对齐的用户"）。
4. **信息层由 agent 主动使用。** 用户的话一律是普通消息，不带 kind、scope、supersedes。约定变了要不要记成 decision、要不要 handoff、要不要提问，都由 agent 自己决定。这同时也在检验 xmuse-collab 技能的提示是否有效。
5. **任务要简单到单人能做对。** 每个成员单独拿到完整信息时都能做对；失败只该来自信息没对齐。
6. 执行者用 `opencode-go/muse-spark-1.3-contributor`（dsh 和 OpenCode），角色和厂商按 seed 交替；需要 Claude 时只用 `claude-haiku-5-5`。shell 策略用 `blocklist-experiment`（agent 要能跑测试；`open-experiment` 会拒绝测试运行器，不能用）。只记录 token，不设预算。

## 1. 对照组

| 组 | 信息层 | 用户（脚本）的做法 |
|---|---|---|
| X | 开 | 只发场景规定的消息 |
| P-dm | 关 | 同样的消息、同样的收件人 |
| P-relay | 关 | 同样的消息，外加：每当有成员发出完成汇报（`kind=done`），就把汇报原文以用户身份私信转给其他每个执行者，开头写"转给你：<成员> 的汇报：" |

P-relay 模拟的是用户现在手动对齐的做法，作为正确率的上限参照。xmuse 想证明的是：**正确率接近 P-relay，而用户的手动转发次数为 0**。

## 2. 场景

每个场景都写清楚：项目文件和归属、初始消息、事件触发的刺激、验收测试要检查什么、过程中要记录什么。

### R1 接口变更（S1 的真实版）
- 项目：`api.py`（A 负责，`get_price(item) -> dict`）、`client.py`（B 负责，`price_label(item) -> str`，调用 `api.get_price`），可见测试只测各自的单元。
- 开始：用户在 `#team` 给两人派活（A 实现 `get_price`，金额字段 `amount` 用"元"、float；B 实现 `price_label`，输出 `"¥12.50"`）。
- 刺激：A 第一次 done 之后，用户**只私信 A**："`amount` 改成用分表示，int。"
- 验收：联调测试，`price_label` 在新约定下输出正确。
- 记录：A 有没有把改动记成 decision（X）或主动告诉 B；B 从什么渠道得知；B 改了几次。

### R2 隔天接手（S2 的真实版）
- 项目：`service.py`、`errors.py`、`log.py`。
- 第一段：用户和 A 定下两条约定：错误一律 `raise AppError(code, message)`，`code` 是大写蛇形；日志前缀 `[svc]`。A 实现功能一。
- 安静下来之后：`xmuse session retire --agent A`。变体 a：用户让 A（新会话）实现功能二；变体 b：新成员 C 实现功能二，A 不再被唤醒。
- 验收：功能二满足两条约定（隐藏测试逐条检查）。
- 记录：两组新会话引导包注入的 token；约定是从唤醒包、文件，还是提问得来的。

### R3 只有一个人知道（S3 的真实版）
- 项目：`sign.py`（A 负责）、`upload.py`（B 负责，要调用第三方接口）。
- 开始：用户私信 A 一个外部事实（"上传接口的签名是 `sha256(key + ts)` 的十六进制小写，`ts` 是秒级时间戳"），并让 A 实现 `sign()`。之后用户让 B 实现 `upload()`，要求带签名头，但不告诉 B 怎么算签名。
- 验收：`upload()` 产生的签名头正确。
- 记录：B 是提问、私信、读 A 的代码，还是猜的；从提问到拿到答复用了多久。

### R4 先后依赖
- 项目：`store.py`（A 负责，要新增 `get_stock(sku)`）、`checkout.py`（B 负责，要用 `get_stock`）。
- 开始：用户一次给两人派活，告诉 B "等 A 的 `get_stock` 好了再接"。
- 验收：联调测试通过。
- 记录：B 在接口出现之前有没有白干、猜接口签名、返工；B 第一次真正动手的时刻和 A 完成时刻的先后。

### R5 共享文件
- 项目：`config.py` 里有一个 `LIMITS` 字典；A 的任务要加 `max_items`，B 的任务要加 `max_amount`，并且都要改 `validate()`。
- 验收：两人的改动都在，测试全过，没有互相覆盖。
- 记录：有没有事先约定分工；冲突改动次数（一方改动被另一方覆盖）。

### R6 失败派回
- 项目：`parse.py`（A）、`format.py`（B），审查者 R 只能跑全量测试、不写代码。
- 开始：A、B 各自实现；R 在两人都 done 之后跑全量测试。题目设计成 B 的部分有一处容易犯的错（例如千分位分隔符），可见测试测不到，全量测试测得到。
- 验收：最终全量测试通过。
- 记录：失败有没有准确送到 B；中间转了几手；B 修好用了几轮。

### R7 侧栏插话
- 项目：A、B 各写一个模块，都要打日志。
- 刺激：A 第一次 done 之后，用户经侧栏（`/v1/act say`，操作令牌）在 `#team` 说"日志一律改成 JSON 格式，字段 `level`、`msg`"。
- 验收：两人最终产出的日志都是 JSON 格式（隐藏测试）。
- 记录：时间线里这条消息的 `from=human`、`via="<vendor> sidebar"`；两人是否都照做。
- 准备：脚本用 `POST /v1/rooms` 建房间，拿到操作令牌（成员 id 用 `user-desk`，vendor 用 claude，hub 不会去运行它）。

### R8 换人
- 项目：一个三步的任务（`step1`、`step2`、`step3` 三个函数）。
- 开始：用户把整个任务派给 A。
- 刺激：A 第一次 done（通常完成了 step1 或 step2）之后，用户暂停 A（`/v1/act pause`），对 C 说"A 有事，剩下的你接着做"。
- 验收：三个函数都正确，A 已经写好的部分没有被 C 重写成错的。
- 记录：C 有没有重做 A 已完成的部分；C 从什么渠道知道进度。

## 3. 指标

- **主要指标**（每个场景一个，开跑前写进预注册）：验收是否通过。各组另外统计**用户动作数**：场景规定之外用户发出的消息数（P-relay 主要是转发次数，X 和 P-dm 应该是 0）。
- **过程指标**：
  - 返工：同一处改了又改回；
  - 空转回合：一个回合没有产生有效改动（文件没变，也没发出有用的消息）；
  - X 组信息层工具的主动使用次数（decision、assumption、question、handoff、resolves）；
  - 唤醒次数、token、墙钟时间。
- **失败归因**：每个失败的 run 判一个原因，分三类：
  - 信息没送到：相关信息从没出现在该成员的唤醒包、收件箱或它读过的文件里；
  - 送到了没照做：出现过，但产出没反映出来；
  - 个人推理错误：信息齐全，照做了，但写错了。

  先由判定器根据唤醒包、消息和读文件记录自动给出初判，再抽一部分人工复核。这条最有用：直接告诉我们该改 hub、改技能提示，还是这本来就不是协作层的问题。

## 4. 执行器改动（在 `experiments/probes/` 上扩展）

- **事件触发**：场景用"事件 → 动作"描述。事件包括 `first_done(member)`、`file_exists(path)`、`quiet(seconds)`、`all_done(members)`；动作包括发消息（用户、或以成员身份）、经侧栏 `say`、`retire`、`pause`、跑审查者的测试。每个阶段有超时。
- **P-relay 转发器**：轮询新的 `kind=done` 消息，按第 1 节的格式转发并计数。
- **判定**：复制工作区 → 放入隐藏验收测试 → 跑 → 记录通过、失败和原文。
- **记录**：每个 run 留下 hub.db、hub.log、每次唤醒的唤醒包、transcript、工作区最终快照、文件改动历史（每个回合结束时对工作区做一次快照或 diff），供失败归因使用。
- 执行器自己的测试：用 `tests/fakes/` 的假 agent 跑通每个场景的事件流程；判定器和失败归因用手工构造的正例、反例测试。不调用真实模型。

## 5. 次数和顺序

1. **在 S 系列已排的第一批之后运行。**
2. 试跑：R1 和 R4 每组各 1 次，只看事件触发、转发器、判定和归因是否正确。
3. 第一批：R1–R4，每个场景每组 5 次，三组交替，角色和厂商按 seed 交替。开跑前提交预注册（场景、主要指标、seed、名单、hub 提交号）。
4. 第二批：R5–R8，同样每格 5 次。
5. 每一步完成后写进 `docs/HANDOFF-BASE-REPORT.zh.md`：各场景三组的通过率、用户动作数、失败归因分布，每类失败附一个典型案例（附唤醒包原文）。

预计规模：8 个场景 × 3 组 × 5 次 = 120 次，每次 10–20 分钟，约 25–40 小时机器时间，可以分批跑。
