## 三、主要发现

1. **对齐层的注入很便宜，但这不等于它有用。** 注入占比每回合最高 0.4%，合计不到 0.1%。
   - 这是因为对齐库只有十几条，而分母很大。它说明的是"成本低"，不是"有效"。
   - 绝对量是每次唤醒几百 token。库还没长大之前，这个数字没有说服力。
2. **完成率 C 78% > B 67% > A 44%，这个差异不能作为对齐层有效的证据。**
   - minisql 是唯一显示组间差别的任务。初版写"开对齐层 3/4 过、不开 0/6 过，单侧 p≈0.03"，**这个结论不成立**，原因有五：
     1. 补跑的 L-3、L-mo-1、L-mo-2 三个开对齐层的 run，这一项都没过。合起来是 3/7 对 0/6，单侧 Fisher p≈0.12。
     2. 初版把 minisql-C-1 当作对齐层起作用的直接证据，但它和日志对不上：第一版实现就是报开引号，question 的结论是保持不变。
     3. 第一回合时 B、C 两组的唤醒包相同，所以第一版选哪种解释，是从同一个分布里抽样。
     4. 这一项是 SPEC 没写清楚的边界，隐藏测试等于在猜题。
     5. 这个任务是从 3 个任务里事后挑出来的，再做检验就有多重比较问题。
   - **准确的说法**：minisql 有一项 SPEC 没规定的边界，各组的第一版实现在两种解释里随机选了一种；对齐层没有表现出能改变这个选择的机制。要回答"对齐层有没有用"，得先把 SPEC 修好，再造一个真正只有一方知道的跨模块约定，然后重测（审计 C3 的 E2）。
   - ledger 没完成的原因是实现质量（全角数字），和对齐无关。pipeline 全部完成，对组别不敏感。
3. **rot 全部遵守（A/B/C 组 27/27，L 组 11 个注入了 rot 的阶段也全部 followed），但这批任务没有区分力。** rot 消息点名了实现方和复核方，并且明说旧测试作废，存在天花板效应。这不能作为"对齐层防 rot"的证据。
4. **申报率（C 52%，A、B 约 67%，L 73%）暂不解读。** 申报由清单匹配判定，而 T1 回放显示匹配器会漏判。例如 ledger-A-1 里 rot 决定的原文被判为"不匹配任何清单项"。指标噪声大、样本小。
5. **复核方能找到预埋的单个 bug：6/6 检出，2 个 run 各有 1 条误报。** 但条件是单回合、SPEC 已知、只埋一个 bug、没有基线。它说明"复核方能找到埋好的单个 bug"，不说明跨 agent 复核比单 agent 自审强。要回答后一个问题，需要审计 C3 的 E5（同一批 bug，单 agent 自审对跨 agent 复核）。
6. **"无人值守"要说准确**：所有 run 在完成或失败时都不需要人插手，max_chain_wakes 一次也没触发。但有两处例外：minisql-C-2 挂在权限确认上约 30 分钟；long-L-2 失败几次后被人工停掉。

## 四、长会话组（L，5 个 run）

同一批会话依次做 ledger → minisql → pipeline，开对齐层；`long-L-mo-*` 另外开了 MemoryOS（见第九节）。

| run | MemoryOS | 用时 | ledger | minisql | pipeline |
|---|---|---|---|---|---|
| long-L-1 | 关 | 694 s | ✓（2 回合；dsh 复核回合 exit 1，**没有复核，rot 未注入**） | ✓ | ✓ |
| long-L-2 | 关 | — | 1 回合后人工停掉，rot 未注入 | — | — |
| long-L-3 | 关 | 903 s | ✗ 全角数字 | ✗ 开引号位置 | ✓ |
| long-L-mo-1 | 开 | 1,089 s | ✓ | ✗ 开引号位置 | ✓ |
| long-L-mo-2 | 开 | 1,039 s | ✗ 全角数字 | ✗ 开引号位置 | ✓ |

- **失败项和短会话组一样**：ledger 挂在全角数字，minisql 挂在开引号位置。long-L-3、long-L-mo-* 的 ledger 原始隐藏测试有 11–12 项失败，其中绝大多数是被 rot 作废的旧约定，按定义不计。
- **注入按设计工作**：换任务时发快照或差量（如 long-L-1 进入 minisql 时发了一次 snapshot），注入占比最高 0.4%。
- **rot**：注入了 rot 的 11 个阶段全部 followed；两次没注入（L-1 ledger、L-2）都是因为 dsh 没有回复复核。天花板效应和第三节相同，**长会话组也不能证明对齐层防 rot**。
- **token**：同一个 run 里，越往后的阶段 token 越高。例如 long-L-mo-1 三个阶段依次是 268 万、464 万、681 万。这和会话越来越长、每次唤醒都要重读上下文一致，但样本只有 4 个完整 run，**没有做量化归因**。
- **样本**：4 个完整 run 加 1 个只剩 ledger 阶段的 run，只能当个案看。

## 六、局限

- **样本**：每组每个任务 3 次，L 组 5 次，复核组 6 次，统计力弱。只报了计数，没有置信区间。
- **口径不一致**：两段的 dsh 模型、运行方式（串行或并行）、hub 代码都不同。
- **任务区分度不足**：rot 全部 followed，pipeline 全部完成；minisql 的差异来自 SPEC 歧义。
- **没有单 agent 基线**：回答不了"多 agent 比一个 agent 强在哪"。
- **只有两个 agent 框架**（OpenCode 和 dsh），后一段用的还是同一个模型，没有 Claude。
- **两个 agent 时，A 组和 B 组的差别测不出来**：几乎每条消息本来就 @ 了对方，测的不是"点名唤醒还是全员唤醒"。要测这一项，至少要 3–4 个 agent。
- **框架问题**（已在后续修复，见 rc/portfolio 的提交）：opencode 权限白名单不认带环境变量前缀的命令；dsh headless 偶发 exit 1。

## 七、下一步

按审计 C3 的优先级：
1. **E1 单 agent 基线**：同一模型，一个 agent 自己实现加自审，三个任务各 3 次。
2. **E2 修好 SPEC 后重测对齐层**：把开引号规则写进 SPEC，另造一个只有一方知道的跨模块约定，B、C 组各 6 次。
3. **E5 复核基线**：同一批预埋 bug，单 agent 自审对跨 agent 复核，各 6 次。

做法上：
- 每个 run 记录 hub 提交号、两边的模型和厂商版本；
- **事先写好主指标和检验方法再开跑**；
- 报告效应量和置信区间。

## 八、T1 离线回放：MemoryOS 能补上 agent 没申报的约定吗

**做法**：取 MemoryOS 关闭时录下的 35 份记录（27 个 A/B/C 组 run、long-L-1 的 3 个阶段、5 个复核 run），用 `experiments/replay_mo.py` 按 hub 的真实触发规则重建 `/curate` 和 `/recall` 请求，离线发给 MemoryOS，再和每个任务的申报清单对比。86 个请求都拿到了响应。

| 问题 | 结果 |
|---|---|
| a) /curate 能补出 agent 没申报的清单项吗 | 35 个 run 里共补出 **7 项**，集中在 3 个 run（ledger-B-2 2 项、ledger-B-3 2 项、pipeline-A-2 3 项）；其余 run 为 0 |
| b) rot 之后能识别"新约定取代旧约定"吗 | 只有 minisql-A-2 出现 1 次 supersedes，而且新旧两条说的是同一件事（都在说 NULL 排序不需要改测试），不是对 rot 本身的识别 |
| c) 提议的噪音 | 共 106 条提议，**74 条（70%）不匹配任何清单项**，0 条和已有条目重复。不匹配的多是复述任务说明或流程规矩，例如"不要 push"、"复核方要跑测试" |
| d) /recall 排序比"按 seq 取最新"好吗 | 有条目的 29 个 run 里，18 个 run 两种方法留下的条目完全一样；命中清单的总数都是 121。/recall 更好 5 次，更差 4 次，**看不出差别** |
| e) 成本 | 22 次 curate 调用，3 次返回 502（都在约 213 秒时）；成功的单次 38–342 秒，中位数约 82 秒；共约 26 万 token（全部有计量） |

**结论**：在这批任务上，MemoryOS 的离线提议**没有显示出正面价值**。补出的项很少，噪音占大头，排序和最简单的基线相当，单次调用还慢。
- 审计据此建议把它降级为可选插件，先做零成本过滤（和任务首条消息相似度过高的丢掉，流程规矩类的用规则丢），再用 `replay_mo` 量化过滤前后的变化。
- 局限：回放是对已有 run 的离线重算，和在线运行时的提议是否一致没有核实；清单匹配器本身会漏判（见第三节第 4 条）。
- 审计写的是"25 次 curate 里 3 次 502"，按回放报告逐行数是 22 次（3 次 502），以本节为准。

## 九、MemoryOS 在线运维（long-L-mo-1、long-L-mo-2）

两个 run 都开着本地 MemoryOS 服务（capabilities：curate、curate.collab、recall、similar），无人值守，提议一律不确认。

| run | /curate 调用 | 失败 | 单次耗时中位数 | token（累计） | 提议 | /recall 调用 |
|---|---|---|---|---|---|---|
| long-L-mo-1 | 5 | 0 | 约 18 秒 | 34,629 | 0 | 0 |
| long-L-mo-2 | 4 | 0 | 单次 20–60 秒（逐阶段中位数 59.5、27.1、19.5 秒） | 27,386 | 5（ledger 4、minisql 1） | 0 |

- 服务日志（`memoryos.log`）里每次 `/curate` 都是 200，健康检查正常，没有 502，没有超时。
- **/recall 一次都没被调用**：对齐库只有十几条，到不了需要召回的上限。所以在线运行验证不了召回的价值，只能靠第八节的离线回放。
- 完成情况和不开 MemoryOS 的 long-L-3 一样，没有看到差别（见第四节）。只有 2 个 run，不做比较。
- token 列取的是每个 run 最后一个阶段的数。按 `metrics.py` 的输出，它看起来是整个 run 的累计值（逐阶段递增），这一点没有逐条核实。
