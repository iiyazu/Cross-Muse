## 三、主要发现

1. **对齐层的成本可以忽略。** C、L 组每回合注入占比最高 0.3%，合计不到 0.1%，远低于 5% 的目标。各组 token 均值相差不到 7%，在单个 run 的波动之内。
2. **完成率 C 组 78% > B 组 67% > A 组 44%，但这个差距主要来自一个任务里的一条约定，不能笼统说"对齐层提高了完成率"。**
   - **minisql 是唯一显示组间差别的任务**：开对齐层的 run（C 组 3 个加 L 组 1 个）有 3/4 通过"未闭合字符串报开引号位置"这一项，不开的（A、B 组 6 个）全部没通过。单侧 Fisher 精确检验 p≈0.03，但样本很小。
   - **机制没有完全核实。** minisql-C-1 里，复核方 dsh 把"位置应该指向开引号还是行尾"提成一条 question 条目，问题被解决后实现改对了，这是对齐层起作用的直接证据。但 minisql-C-2 里没有相关条目也通过了；而 A 组 minisql-A-1 的实现方明明申报了"position 是 0 起的字符偏移"，仍然没通过。所以只能说"开对齐层时更容易把这个边界情况对齐"，因果链只有 1 个 run 的直接证据。
   - **ledger 的失败和对齐无关**：全角数字没被拒掉是实现质量问题，A 组 2 次、C 组 1 次，B 组 0 次。
   - **pipeline 全部完成**，对组别不敏感。
3. **rot（中途改约定）全部遵守：27/27 个 A/B/C run，加 L 组 2 个注入了 rot 的阶段。** rot 消息 @ 了实现方和复核方，并说明旧测试作废。在这种条件下，不管有没有对齐层，agent 都能跟上新约定。因此这批任务没法检验对齐层在 rot 上的价值；它可能在更长、更多人参与、或者 rot 没有点名到每个人的场景里才显现。
4. **申报率 C 组反而最低（52%，A、B 组约 67%）。**
   - 后段有 3 个 run 申报数是 0：ledger-B-2、minisql-C-2、pipeline-A-2，分布在三个组。
   - R6 加强了出口检查，仍然不够稳定。
   - C 组更低的原因没有核实。一种推测是：开了对齐层，实现方觉得"条目里已经有了"，就不再在交接时申报。
5. **复核方表现好**：单回合复核 5/5 检出预埋 bug，误报 2 条。
6. **全程无人工干预**：33 个 run 没有一个需要人插手，max_chain_wakes 一次也没触发。

## 六、局限

- **样本**：每组每个任务 3 次，L 组和 review 组各 1 轮，统计力弱。
- **口径不一致**：两段的 dsh 模型和运行方式（串行/并行）不同；token 和耗时不能跨段比较，完成率和 rot 不受影响（判定标准相同）。
- **任务区分度不足**：rot 全部 followed、pipeline 全部完成，这两项对组别不敏感。要拉开差距，需要更多跨模块约定、更长的会话，或者 rot 不点名到所有人。
- **只有两家 agent**（OpenCode + dsh），没有 Claude。
- **框架问题**：
  1. opencode 的权限白名单不认带环境变量前缀的 shell 命令，例如 `PYTHONPATH=... python -m ...`，无人值守时会挂到回合超时。下一轮实验前要修。
  2. dsh headless 偶发 exit 1 或卡死，hub 能靠重新唤醒恢复，但单回合的 review 场景恢复不了。要在适配器里给预检和回合加一次重试。
- **MemoryOS 没参与**：MemoryOS 的价值留给 T1 离线回放和 T3 的 long-L-mo 评估。
