- clowder-ai 的 UX 调研，见 `dsh-work/d12/topo/CLOWDER-UX.zh.md`。

## 1. 目标和验收

**目标**：用户只需记住三样东西——项目、Claude、助手。房间、成员 id、会话、令牌全部退到后台。协作拓扑（谁负责什么、谁和谁一组、怎么派活）不由产品预设，用户怎么用就怎么组织。

**验收**（用户在真机上走一遍）：
1. 在 Claude 桌面 App 打开某个项目的会话，右侧自动出现 xmuse 面板。不需要命令，不需要开房间，不出现任何 id。
2. 点一下"+ OpenCode"，OpenCode 助手出现在面板里，状态显示"空闲"。
3. 在面板里选中 OpenCode，打一句话，回车。面板里能看到它在干活：执行中、计时、工具数，回复以流式出现。
4. Claude 用工具把活派给 dsh，dsh 交回后，Claude 被自动叫醒，接着往下干。
5. 助手要执行白名单之外的命令时，面板顶部出现审批卡，点一下就处理完。
6. 关掉 App 第二天再打开，同一个项目里还是那个 OpenCode。它记得昨天做了什么，用户从没看到过"会话"二字。

第 1 到第 3 步合计不超过三次操作。

## 2. 心智模型

| 用户看到的 | 背后是什么 |
|---|---|
| 项目 | Claude 会话的工作目录。一个目录对应一个 hub，一个房间。房间对用户不可见 |
| Claude | 桌面 App 里的这个会话，永远是主控，hub 不驱动它 |
| 助手（OpenCode、dsh，以后可以接入更多） | 由 hub 驱动；默认成员 id 就是厂商名。它的会话、记忆、上下文都在后台。负责什么由用户决定：可以写在职责描述里，也可以在派活时临时说明 |
| 对话 | 面板里每个助手一个私聊页签，外加"全部"（#room）页签，再加用户或 Claude 建的小群页签 |

- 默认每家一个助手，这是 v1 的默认值（用户 10-12 定），不是架构限制。hub 本来就支持同一厂商多个成员，以后在面板上放开即可。
- 已有的拓扑能力全部保留，并在面板里可用：私有小群（T2）、主控分派（T0）、私信分享审批（T3）。按职责路由（T4）会叫醒没被 @ 的助手，和总线规则冲突，改成默认关闭的开关。
- 用户直接对助手说的话，默认不让 Claude 看到。这一条沿用"私信分享需批准"的规则，分享要用户点头。Claude 为了派活转述任务内容是允许的；不外传的是用户个人的事实和偏好（用户 10-12 确认）。

## 2.1 消息总线（用户 10-12 定）

面板的逻辑角色是**消息总线的窗口，主要面向用户**。规则按发送方不对称：

| 谁发 | 带 @ | 不带 @ |
|---|---|---|
| 助手（包括 Claude） | 推送：叫醒被 @ 的人，直接收到 | **非对齐信息**：留在总线上，逻辑上是给用户看的。其他助手要主动查才看得到（叫醒时只附一行"另有 N 条未读"） |
| 用户 | 推送：叫醒被 @ 的人 | **广播**：立即叫醒所有助手（Claude 由 mod 叫醒），全文送达 |

- **用户发私聊**：在 Claude Code 主对话里说话，就是和 Claude 私聊；在面板里可以选某个助手私聊，或者发到总线。
- **回复继承推送**：回复一条 @ 了自己的消息时，自动推送给原发送人，助手不用记得写 @。现在只有"问题"类型有这个行为（`mail._routed`），要推广到普通回复。
- **小群就是小号的总线**，规则相同。
- **@用户**：推送到用户这边，也就是面板里的"@你"标记、状态行和 toast。
- **信息层的位置**：总线放过程，信息层放结论。决定、假设、问题、派活的理由会变成条目，按作用范围推送给相关助手（第一次给快照，之后给增量）。会话轮换的交接包也由条目生成。广播只是把消息送到每个人手里；想让一句话长期有效，在面板上对那条消息点"设为决定"。
- **主动发言**：助手只在被叫醒的回合里发消息，空闲时不会自己开口，这是有意的。防止互相 @ 来回打转，靠连锁对话的叫醒次数和 token 上限，以及 T7。

## 2.2 安装与拉人（用户 10-12 定）

**① 第一次安装：登记本机能用的 agent（全机一次）**
- 第一次打开 xmuse 面板时显示"设置助手"页。
- 自动扫描 xmuse 适配过的各家（现在是 OpenCode、dsh）：装没装、版本。复用 `xmuse doctor` 的检查。
- 试跑：每家用默认模型跑一个极小回合（"回复 OK"），证明登录、额度、模型都正常。只有试跑通过的才算"能用"。
- 每家可以选默认模型。
- 结果存进本机助手登记表（和房间登记表同一目录，例如 `agents.json`）：厂商、命令路径、默认模型、验证时间、状态。凭据留在各家自己的登录里，xmuse 不读、不存。
- 设置页有"重新扫描"，装了新 agent 时用。
- Claude 作为被 hub 驱动的助手（`claude -p`）从 2026-06-15 起单独计费（见 clowder 调研 F198），扫描结果里单独标注，默认不勾选。

**② 新项目**：在 Claude 里打开项目，开启面板，房间自动建好（H1）。面板列出登记表里能用的助手，勾选即拉进本项目，不需要输入厂商名、模型或 id。

**③ 中途拉人**：点"+ 助手"选一个。新助手第一次被叫醒时拿到入场包（H12）：
- 现有的新会话交接包：身份和职责、按作用范围筛选的现行决定、约定、分工、未决问题，以及各相关群最近 8 条消息；
- 新增"项目简介"：开房间时由 Claude 写一条全局作用范围的条目（目标、技术栈、约定），之后有助手加入就自动带上；
- 新增"进行中的活"：谁手上有什么活、做到哪了。
- 助手加入时通知 Claude，Claude 可以直接派活。

## 3. 前端：Claude mod

### 3.1 面板（右侧停靠）

从上到下：
1. **助手条**：每个助手一个圆形 SVG 头像，加彩色名字和一行状态（● 执行中 1:12 / ○ 空闲 / ⏸ 已暂停 / ⚠ 等审批），最右边是"+ 助手"。
2. **页签**："全部"、每个助手的私聊、各个小群，未读数标在页签上。页签栏末尾有"+ 群"：选几个助手建私有小群。助手的职责描述在助手条上点开就能改。
3. **审批卡**：固定在顶部，琥珀色边框，按钮是"批准一次 / 总是批准 / 拒绝"。没处理就一直显示。
4. **消息流**：每条消息带头像、彩色名字、"→ 发给谁 · 时间"，正文是圆角气泡里的 Markdown。和 Claude 的回复用同一个渲染器，表格、代码高亮、链接都和 Claude 一样。改动用 diff 代码块显示。执行过程折叠成一行"已完成 · 9 个工具 · 1 分 49 秒"，点开才看明细。
5. **执行条**：每个在干活的助手一行，显示计时、工具数、排队 N 条，带停止按钮。
6. **输入栏**：发给当前页签的对象。在"全部"页签里，不带 @ 就是广播，带 @ 就推送给被 @ 的人（见 2.1）。每条消息上都有"设为决定"按钮。

样张见 xchat（在 mod 目录里），已在桌面端实测。

### 3.2 面板以外的部分

- **状态行**（输入框下方）：一行概括，例如"xmuse · OpenCode 执行中 · 1 条待审批"。用户不看面板时，靠它提醒。
- **派活工具**：给 Claude 注册 `xmuse_send` 一类的工具，沿用现有的 `xmuse_*`。Claude 派活、交回都走这些工具。
- **叫醒 Claude**：助手的回复是发给 Claude 的，就由定时器调用 `$.prompt.submit` 起一个回合。D0 和本次探针都已验证可行。
- **斜杠命令**只留兜底的几个：`/xmuse`（打开面板）、`/xmuse-add`。日常操作都在面板里点。

### 3.3 助手回复放在面板里（用户 10-12 定）

助手的回复只在面板里显示，不插进主对话。@Claude 的消息由 mod 叫醒 Claude 直接处理。

### 3.4 写法约束（实测得来）

- `$` 只能传给文件顶层声明的函数，否则整个模块不加载。
- Markdown 的内容放在 `text` 属性里，不能写成子元素。按钮必须带 `onPress`。SVG 的宽高单位是像素。
- 界面元素在桌面端有校验，类型检查查不出来，所以每个界面都要在桌面 App 里实际打开看一遍。
- 现有的 `integrations/claude-mod`（1487 行）从没在真会话里加载过。T8 按探针的写法重做，旧代码只借用里面的逻辑。

### 4.1 压缩：何时压、怎么压得好（H3 详述）

**为什么不换新会话、只压缩**（用户 10-12）：会话里有提示词缓存，频繁换会话或压缩都会让缓存失效，很贵。所以维持原则 9，只加一条系统兜底，其余交给用户自己决定。

**何时压缩**
- **系统兜底**：助手空闲（不在回合中）、上下文超过 50 万时，hub 自动压缩一次。不在回合中途压缩。
- **用户手动**：面板的助手条上显示上下文大小（例如"42 万"），点开后有"压缩"按钮。
- Claude 自己的会话：照旧由用户在 Claude Code 里 `/compact`，或者由 Claude Code 自动压缩。

**怎么压得好：hub 生成压缩指令**
hub 手里有每个助手的同步信息，用它拼出一段压缩指令，等同于用户以前让 Claude 写的 `/compact` 提示词：
- **必须保留**：它手上未交回的活，以及每件活的目标、进度和下一步；它最近交回的结果摘要；它改过的文件和分支；还没解决的问题；用户对它说过、仍然有效的要求。
- **可以丢掉**：工具输出的原文、已经交回并确认的活的过程细节、被取代的决定。
- **不用复述**：现行的决定和约定。压缩后 hub 会自动重发对齐快照（现有机制：上下文骤降即视为压缩过），所以摘要里不必重复，能压得更小。

**各家能不能接受这段指令**
| 对象 | 怎么接 | 状态 |
|---|---|---|
| Claude（主控） | mod 钩住 `session.compact` 事件，把 hub 的指令追加到 `instructions`。手动 `/compact` 和自动压缩都会经过这个钩子，用户不用再自己写压缩提示词 | 接口在类型文件里有，未实测 |
| OpenCode | 能外部触发：`POST /api/session/{id}/compact`（参数只有 delivery，默认在下一步边界执行）。调用时带不了指令，指令要写进实例配置 `opencode.json` 的 `agent.compaction.prompt`，hub 本来就会写这个文件。事件有 compaction started、ended、failed | T8c0 探针（10-12，oc-d4 #112）。缓存表现未确认：测试服务没有模型凭证 |
| dsh | 未知 | 未确认，T8c 先做探针 |

不能带自定义指令的厂商退一步处理：压缩照常进行，压缩后 hub 把对齐快照和"你最近交回的结果摘要"一起重发，作为事后补齐。

**验证**：T8c 交付时做一个探针，压缩前后各问同一个关于当前任务的问题，比较答案。同时记录压缩前后的上下文大小和缓存命中情况。

## 8. 风险

- **mod 接口还是早期版本**，会跟着 Claude Code 版本变（实测版本 2.1.295）。对策：界面代码集中在一个文件；每次升级先跑一遍 xprobe。
- **hub 在 WSL，mod 在 Windows**：连通性已实测（HTTP、`\\wsl.localhost` 读文件、`wsl.exe` 都通）。`sidebar.key` 在 WSL 的状态目录里，mod 经 UNC 路径读取。
- **压缩丢信息**：靠 hub 生成的压缩指令和压缩后的对齐快照接住。T8c 交付时做探针：压缩前后各问同一个问题，看答案是否一致。
