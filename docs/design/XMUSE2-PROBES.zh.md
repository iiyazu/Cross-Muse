# xmuse 2 信息协作层：机制探针（审定稿，2026-10-12，r7）

**状态**：用户定下方向（不在屎山代码库上做实验，按信息协作层愿景里的功能逐个做小而确定的验证），r7 审定，交给 base 实现。本稿以 base 的草案 `T17-MECHANISM-PROBES.zh.md`（69d816d）为底：玩具世界、P 由脚本扮演、三组对照都保留；在此基础上定下 T17 第 5 节的三个待定问题，补上产品功能探针，并改掉读代码时发现的几处问题。两份文件不一致的地方，以本稿为准。T16 草案作废，T15 只写成"低协作需求下的基线和开销测量"，不做两组对比。

## 0. 原则

1. **一个探针只测一个功能。** 工作区是玩具世界，刺激由脚本按固定文本、固定时刻发出，判定由程序完成。做不对就说明这个功能在真实 agent 上不可靠，定位直接。
2. **不比个人推理能力。** 任务本身要简单到每个执行者单独都能做对，错只能错在信息没有到位。
3. **对照组要公平。** 只在有自然替代做法的地方设对照，而且对照组拿到的信息量不能比 xmuse 组少：同样的文本、同样的时刻，只是没有信息层的结构。
4. **只记录，不设预算。** token、唤醒次数、耗时全部记下来。
5. **执行者用便宜模型。** dsh 和 OpenCode 都用 `opencode-go/muse-spark-1.3-contributor`；需要 Claude 时只用 `claude-haiku-5-5`。

## 2. 机制探针（玩具世界）

玩具世界、tick 推进、`out/<agent>/<key>` 的写法、判定标签（正确、越权写、空缺、值错）都按 T17 第 1 节。下面只写和 T17 不同、或者需要补充的地方。

### S1 取代传播（用户给的例子）
按 T17。补充一条判定：除了越权写和空缺，还要记录 X 组 E2 下一次唤醒的唤醒包里有没有出现被取代的条目和新条目（从 hub 日志或 `turns.align_mode`、唤醒包文本里取）。这样失败时能分清是"信息没送到"还是"送到了没照做"。

### S2 新会话后的持久化
- hub 默认不会自动换会话（设计 §4.1 原则 9：只有在没有当前会话时才开新会话）。**不要直接改数据库**，给 hub 加一个小的管理功能：`POST /v1/admin/retire {"agent"}` 和 CLI `xmuse session retire --agent <id>`，把这个成员当前的会话标为已退役，下一次唤醒就开新会话。它本身也是产品功能（用户想让某个成员"从头开始"），要带测试。
- **对照组要公平**：新会话的引导包里，P-dm 和 P-bc 组拿到的是线程里最近的原始消息（`recent_n`，默认 8 条），X 组拿到的是条目快照加最近消息。为了让比较落在"结构化条目 vs 原始消息记录"上，而不是"有记忆 vs 没记忆"，在 tick 0 的决定和 tick 4 之间要插入足够多的 tick 消息，让决定落到 `recent_n` 的窗口之外。两组注入的 token 都要记录。

### S3 问答 + 依赖唤醒（要改设计）
读代码确认：`kind=question` 的自动路由，唤醒的是**给提问者派活的人**（提问者当前有效 assignment 的作者），不是知道答案的人（`mail._routed`）。按 T17 的写法，E1 的任务是脚本 P 派的，E1 提的问题会路由到 P（人类），而 P 是脚本、不会答，于是 X 组会必然失败。这测到的是脚本的空白，不是信息层。改成下面两个变体，都做：
- **S3a 派活人就是知情人**：k 只私信给 E2，由 E2 给 E1 派这个任务（脚本以 E2 的令牌发出 handoff，正文固定，不提 k 的值）。X 组里 E1 的 question 会路由回 E2；对照组里 E1 只能自己想到去私信 E2。判定：e 正确的 tick 占比、从提问到答复的耗时。
- **S3b 知情人只能靠职责描述找到**：任务由 P 派给 E1；E2 的职责描述里写"持有系数配置"。判定 E1 有没有找对人。这一变体其实同时在测按职责委派（见 P1）。如果 X 组明显失败，结论就是"question 应该能按职责描述路由给知情人"，写进报告，作为信息层的一个缺口。

依赖唤醒单独测：给 E1 的 handoff 带 `depends_on`，指向一个还没答复的 question 条目；脚本在固定时刻答复（`--resolves`）。判定：答复之前 E1 没有被唤醒（看 `turns.started_at` 和答复时刻），答复之后 E1 用上了答复的内容。

### S4 噪声下的定向信息、S5 冲突与时间顺序
按 T17。S4 的 module 作用域要先让负责 c 的执行者"拥有" module:c（用带 `--scope module:c` 的 handoff 派给它），否则 module 条目送不到任何人。

## 3. 产品功能探针（第二批）

这些测的是信息层之外、用户在愿景里要的功能。大多数只看通过率，不设三组。

| # | 功能 | 场景 | 判定 | 对照 |
|---|---|---|---|---|
| P1 | 按职责描述委派 | 三个执行者，id 用中性的 m1、m2、m3，各有一条职责描述（`xmuse agent add --description`）。协调者由 LLM 担任（OpenCode）。用户在 `#room` 提一个需求，不点名任何人 | 协调者把 handoff 派给职责对口的那个成员 | 去掉职责描述（只有中性 id） |
| P2 | 规则化审批 | OpenCode 执行者按脚本依次请求三类命令：普通命令、危险命令（`git push`）、本机 curl | 在宽松策略下，普通命令和本机 curl 自动放行，危险命令被挂起；挂起的那条出现在 `/v1/view` 的 `approvals` 里，用操作令牌批准后命令继续执行 | 只看通过率 |
| P3 | 经侧栏介入 | 用户（操作令牌）经 `/v1/act say` 发一条新约定 | 执行者后续都照做；时间线里这条的 `from` 是 `human`、`via` 是 `"<provider> sidebar"` | 只看通过率 |
| P4 | 跨厂商矩阵 | S1–S3 在 dsh↔dsh、OpenCode↔OpenCode、dsh↔OpenCode 三种组合上各跑；Claude haiku 只做一组 dsh↔Claude | 各组合的通过率 | 矩阵本身就是对比 |

P3 的限制：约定 v0 的 `say` 只能发普通消息，不能带 `kind=decision`。P3 先测普通消息，约定 v0.1 给 `say` 加 `kind` 之后再补一个"侧栏发 decision"的变体。

## 4. 执行器

- 位置：`experiments/probes/`。`run.py`（驱动）、`judge.py`（判定）、`report.py`（汇总）、`scenarios/`（场景定义）。场景定义用 JSON 或 Python 模块都行，不要引入新依赖。
- 每个 run：新建临时工作区（dsh 要求在 Windows 盘上，位置由 base 按 T15 的经验定，跑完移走）→ `xmuse init` → 写 `config.json`（`info_layer`、需要的话 `recent_n`）→ 按场景加成员 → 起 hub → 脚本按时刻发 tick 和刺激 → 等 done 或超时 → 判定 → 收集 hub.db、hub.log、唤醒包和 transcript → 停 hub。
- 刺激一律走 CLI 或 HTTP 接口（`xmuse send`、`xmuse tool --agent`、`/v1/act`），不直接写数据库。S2 的换会话走新加的 `xmuse session retire`。
- **`xmuse send` 现在发不出脚本要的几种刺激**（读代码确认）：CLI 只有 `--kind`、`--scope`、`--supersedes`、`--mention`、`--idem`，`admin_send` 也只传这些。以人类身份发 handoff 要带 `why` 的五个字段，答复要带 `resolves`，依赖要带 `depends_on`，现在都传不了。给 `xmuse send` 加 `--args-file <json>`（和 `xmuse tool` 一样，JSON 里可以带 `why`、`resolves`、`depends_on`），`admin_send` 把这些字段传给 `mail.send`，带测试。以执行者身份发出的固定刺激（如 S3a 里 E2 的 handoff）用 `xmuse tool --agent <id> send --args-file`。
- 输出：每个 run 一个 JSON（场景、组别、序号、逐 tick 判定、主要指标、token、唤醒次数、耗时、提交号），汇总成 Markdown 表格和逐 tick 曲线。
- **执行器自己要有测试**：用仓库里现成的假 agent（`tests/fakes/`）跑通每个场景的流程；判定器用手工构造的正例和反例 `out/` 目录测试。这些测试放进 `tests/`，不调用真实模型。

## 5. 次数和流程

1. **试跑**：S1 每组 2 次，只检查刺激有没有送到、判定器对不对、唤醒包里有没有该有的条目，不看分数。不对就先改，再试跑。
2. **第一批**：S1、S2、S3a、S3b、依赖唤醒，每个每组 10 次，三组交替进行。开跑前把场景定义和主要指标提交进仓库，作为预注册。
3. **第二批**：S4、S5、P1–P4。
4. 每批跑完写进 REPORT：每个场景的主要指标（三组的均值和区间）、失败的典型案例（附唤醒包原文）、发现的信息层缺口。
