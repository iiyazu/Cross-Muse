## 0. 结论先行（10 条）

1. **工程底子是真的，叙事比证据跑得快。** hub 只有约 3,800 行 Python，单写线程 + SQLite + 幂等 + 会话租约 + 压缩信号 + 崩溃重放去重，这些都是踩过坑的真本事，面试能讲很久。但"对齐层提高完成率"这个核心结论**目前不成立**（见第 4 条）。
2. **规划方有一处事实错误**：`m2b`（`893722a`）**已经是** `dsh/bundle`（`baa8b24`）的祖先（`git merge-base --is-ancestor 893722a baa8b24` 成立）。没合进来的只是 m2b 工作树里**未提交**的 `experiments/results/`（`.gitignore` 注释写着"results/ is committed"，实际是 `??`）。所以"集成分支"不用新建，`dsh/bundle` 就是，缺的是把它合进 `main`（要先问用户）和提交实验数据。
3. **实验报告已过期**：报告写于 10-10 19:01，之后又跑了 `long-L-3`、`long-L-mo-1`、`long-L-mo-2`、`review-ledger-bug1-1`（这次成功了），结果没进报告。
4. **minisql 的"p≈0.03"不成立**：
   - 加上报告之后的 3 个长会话 run，minisql 的开引号这一项在开对齐层的 run 里是 **3/7**（C-1、C-2、L-1 过；C-3、L-3、L-mo-1、L-mo-2 不过），关对齐层的是 0/6，单侧 Fisher **p≈0.12**；
   - 报告说 minisql-C-1 里"问题被解决后实现改对了"，**与日志不符**：实现方第一版就把位置指向开引号，dsh 的 question 问的是"要不要改成 len(sql)"，结论是"保持不变"（`minisql-C-1/log.txt` 第 20、37、56 行）；
   - 实现方第一回合时对齐库是空的，B 组和 C 组第一回合的唤醒包在 `wakepack.render` 层面相同，所以"第一版选开引号还是 len(sql)"是同一分布下的抽样；
   - 这条本身是 SPEC 没规定的歧义项（SPEC §3 只写"没有闭合 → ParseError"，而通用规则"出错位置在语句末尾时用 len(sql)"反而指向另一个答案），隐藏测试等于猜题。
   结论：**这批数据只能支持"对齐层便宜、不碍事"，不能支持"对齐层有用"**。
5. **"跨厂商"在后 21 个 run 里只是"跨外壳"**：dsh 从 `46d5a14` 起默认用 `opencode-go/muse-spark-1.3-contributor`，和 OpenCode 是同一个模型，但 `config.py` 的 `FAMILIES` 仍把 dsh 标成 `deepseek`，唤醒包里给同伴看的 `family="deepseek"` 是错的。
6. **MemoryOS 目前没有正面证据**（T1 回放）：/curate 在 35 个 run 里只补出 7 个清单项（集中在 3 个 run）；106 条提议里 74 条不匹配任何清单项（大量是复述任务说明和流程规矩）；/recall 的排序和"按 seq 取最新"几乎一样；25 次 curate 里 3 次 502，单次 40–340 秒。建议降级为可选插件，停止追加投入。
7. **最大的结构性风险是信任模型**，不是并发：
   - agent 能读到所有令牌，包括管理令牌：Claude 放行了 `python3`，OpenCode 默认放行 shell，dsh 有 PowerShell；`.xmuse.json` 还把状态目录路径写在工作区里。拿到 `_admin` 就能自己批准 `git push`（`/v1/admin/approve`）、确认提议、恢复被暂停的 agent；
   - "有后果的命令要人批"靠的是 fnmatch 黑名单（`opencode.py:29-79`），`cd x && git push`、`bash -c "git push"`、`python3 -c "subprocess…"` 都能绕开；
   - 设计稿 §4.2 写的"agent 读不到令牌"不成立。
8. **方向 8（Jev 决策点）现在做是过度设计**：没有标注数据可供校准，外部托管违背设计稿自己"关遥测"的隐私口径，面试官跑不起来，厂商数据无法核实。"决策点"这个**抽象**值得做，但后端先用规则，再用便宜 LLM，离线评测和影子模式日志才是要展示的东西（第 6 节）。
9. **唤醒成本的可省空间比想象小**：中位数每次唤醒 27 万 token，95% 是缓存读；对话型唤醒占 32% 的回合，但只占 11% 的 token。确定性的修补（不为已 ack 或已读的投递再唤醒，见 B2-3）能拿到大部分收益，不需要模型判断。
10. **作品集的第一缺口是"别人能跑起来、能看懂"**：没有顶层 README，没有 LICENSE 和 CI；797 个跟踪文件里 561 个是 `spikes/` 和 `e2e/results/`；路径里写死了 `/home/user`、`Ubuntu-24.04`、`C:\Users\<WSL 用户名>`；dsh 只有 Windows 版而且是 rc。还缺**单 agent 基线**：面试官第一个问题会是"比一个 agent 自己做强在哪"，现在答不上来。

## B. 架构与代码质量

### B1. 总体评价

优点（面试可以讲）：
- **规模克制**：hub 约 3,800 行 Python，加上 TS 垫片 106 行、dsh bundle 505 行；对比 v1 约 10 万行，"砍掉平台、只留协作层"这个演进叙事有说服力。
- **状态集中**：所有事实在 `hub.db`；`deliveries` 每个收件人一行，状态机清楚；`BEGIN IMMEDIATE` 串行写（`db.py:118-127`）；重启时把运行中的回合标为失败并重新排队（`engine.py:313-321`）。
- **幂等**：`send` 按血缘去重（`mail.py:104-114`），`done` 按内容哈希去重（`mail.py:235-242`）。这正好对应 dsh 崩溃后续接会重跑被杀回合的实测行为。
- **确定性的对齐层**：申报直接入库、显式 supersede、水位和差量、作废通知，热路径零 LLM；`wakepack` 是有名字的处理器管线，输出稳定，有利于前缀缓存。
- **防失控**：链唤醒上限、每小时回合和 token 上限、厂商限额重排队、`xmuse stop`。

### B2. 风险清单（按严重程度排序）

**B2-1 信任模型：令牌对 agent 可见，管理令牌等于人的全部权力**（高）
- 令牌在 `~/.local/state/xmuse/<ws>-<sha8>/tokens/`，权限 0600，但 agent 和 hub 是同一个 OS 用户。Claude 的白名单带 `python3`；OpenCode 默认放行 shell；dsh 有 PowerShell，能读 `\\wsl.localhost\…`；dsh bundle 本身就从 Windows 侧读令牌（`index.js:166-172`）。
- 拿到 `_admin`，就能调用 `/v1/admin/approve`（自己批准自己的 `git push`）、`/v1/admin/align`（确认提议）、`/v1/admin/resume`、`/v1/admin/send`（以 human 名义发消息，虽然会标 `via=cli`）。见 `server.py:143-205,316-319`。
- 身份绑定（`server.py:214-229`）校验的是**客户端自己报上来**的 `x-xmuse-session` 头，只防同一个 bundle 里的兄弟会话误用，不防恶意。
- 定性：这是"防误操作"的单用户信任模型，不是"防恶意 agent"。设计稿和对外文字都要照实写。
- 改进，按成本从低到高：
  1. 审批改成必须由人在终端交互确认，不能用令牌 API 完成（例如 `xmuse approve` 要求 TTY 并读一次性确认码）；管理令牌不放在 agent 能 `cat` 的目录。
  2. agent 进程用单独的 OS 用户，或者用 bubblewrap/firejail 启动 headless agent，把状态目录挡在外面（Windows 侧的 dsh 做不到，要写明）。
  3. "有后果"的边界放到 git 层：agent 的环境里不给推送凭据，加 pre-push 钩子，每个 agent 一个 worktree（即 M3）。

**B2-2 shell 自动批准是黑名单，容易绕开**（高）
- `ASK_SHELL` 是 fnmatch 的前缀模式（`opencode.py:29-30`），`shell_auto_ok` 只剥掉环境变量前缀（`opencode.py:67-79`）。`cd sub && git push`、`bash -c "git push"`、`git -C . push`、`/usr/bin/git push`、`python3 -c "import subprocess; …"`、`gh pr merge`、`npm publish`、`scp`、`ssh` 都不会被拦（多数在 OpenCode 那一层就不会触发 ask，hub 根本看不到）。
- 这是"提醒"，不是"边界"。真正的边界只能是 B2-1 第 3 点。实验跑起来顺是因为任务里本来没人想推送。
- 建议：保留黑名单作为减少打扰的启发式，但在设计稿和 README 里**明说它不是安全边界**；注入/越权测试套件（方向 5）应该把这些绕过写成用例。

**B2-3 浪费的唤醒：已 ack 或已读的投递仍会触发下一次唤醒**（中，最容易修）
- `_admit` 选待投递消息时只看 `d.state='queued' and d.wake=1`（`engine.py:96-99`），不看 `acked_at` 和 `read_at`。agent 在自己回合中途用 `xmuse_inbox` 读到、甚至 ack 了的新消息，回合结束后还会被再唤醒一次。
- 实例：`minisql-C-1` 的 turn 7，dsh 花了约 20 万 token，只说了一句"No new work: … duplicates of items already handled last turn"。粗略正则统计，341 条 done 里约 33 条（约 10%）是这类"没有新事"。
- 修法（确定性，几十行）：
  1. 已 ack 的投递在准入时直接置为 done；
  2. 在本 agent 运行中的回合里被读过的投递，回合结束后只在"本回合没有对它们作出回应"时才唤醒，或者改为下一次唤醒时附带、不单独唤醒；
  3. 一个很短的去抖窗口（2–5 秒），合并同一收件人的连发。

**B2-4 dsh 依赖 rc 版本的内部入口**（中高）
- headless 路径用 `--expose-internals` 加 asar 里的内部路径 `dsh-desktop-host/lib/cli.js`（`dsh.py:111,206`），安装目录写死为 `/mnt/c/Users/$USER/AppData/Local/Programs/DeepSeek Harness`（`dsh.py:109-110`；这里的 `$USER` 是 WSL 用户名，默认它和 Windows 用户名相同）。
- bundle 的 `peerDependencies` 把三个 `@deepseek-ai/*` 包**精确钉死在 `0.2.0-rc.2`**（`package.json`），这和插件调研 §1 的建议（"不声明 peer"）相反。按调研，profile 导入时会校验 peer 范围，dsh 一升级到 rc.3，插件就会被拒载（提交 `c35ba98` 说明了为什么这样做，但没说明怎么应对升级）。
- 建议：
  1. 用范围（`>=0.2.0-rc.2 <0.3.0`）加启动自检（探测 `sessionController.resolveAgent`、`agent.followup` 是否存在，不存在就惰性并打日志）；
  2. 在 README 写明验证过的 dsh 版本，加一个 `xmuse doctor` 检查项；
  3. 对面试的说法：dsh 是"第三家的接入样例"，核心价值不依赖它。

**B2-5 Windows/WSL 桥的可移植性**（中，对作品集是高）
- 写死或默认的路径：bundle 的 `DEFAULT_STATE` 和 `cordis.patch.yml` 写死 `\\wsl.localhost\Ubuntu-24.04\home\user\…`；`WSL_DISTRO_NAME` 缺省为 `Ubuntu-24.04`（`dsh.py:46-47`）；`WIN_HOME`（`dsh.py:109`）。
- 约束：dsh 工作区必须放在 `/mnt/<drive>/` 下，于是 Claude 和 OpenCode 也要走 9P 访问 `C:\`，慢。
- 依赖的小技巧：`WSLENV` 透传、`MSYS_NO_PATHCONV=1`、wsl.exe 会重新拼接参数（所以要 `--args-file`）。这些都写进了代码注释，但没有集中成一份"平台矩阵"。
- 建议：路径全部从 `xmuse init` 生成的配置里读；加 `xmuse doctor`，检查 distro、Windows 用户目录、dsh 版本、端口转发、node、opencode、claude 版本；README 给一张"Linux 原生 / WSL / Windows"的支持矩阵，Linux 原生下 dsh 显示为不可用。

**B2-6 并发：实现和注释不一致**（低–中）
- `engine.py` 文件头写"Every other thread only enqueues events"，但 `mail.send/inbox/ack`、`relay_*`、`DshDriver._adopt` 都在 HTTP 线程里直接写库。靠 SQLite 的 `BEGIN IMMEDIATE` 和 `busy_timeout=30000` 串行化，目前正确，但"单线程状态机"的说法不成立。
- 两处跨线程的普通字典：`DshDriver.human`、`OpenCodePrompt.human`（HTTP 线程或 SSE 线程写，引擎线程读）。在 GIL 下单次操作是原子的，问题不大，但应该注释说明或加锁。
- `_admit` 先在事务外读待投递列表，再在事务里更新（`engine.py:96-131`）。和它竞争的写者都在 HTTP 线程上，只改 `read_at` 和 `acked_at`，不改 `state`，所以目前不会出错。
- `relay_poll` 一次占住一个 HTTP 线程最多 25 秒，几个 agent 时没问题，规模上去要改成事件驱动。
- 建议：把注释改成"状态迁移（准入、完成、取消）只在引擎线程；消息写入在请求线程，靠 SQLite 串行化"，再补一个并发测试：多个线程同时 `send` 和 `ack`，同时引擎在准入。

**B2-7 适配器边界是隐式的**（低–中）
- `engine.py` 直接 import `opencode.shell_auto_ok`（第 16 行），`admin_approve` 写死 `drivers["opencode"]`（`server.py:195`）；`presence/push/headless/on_hook/register_shim/attach_command/write_config` 是靠鸭子类型的约定，`adapters/base.py` 没有把它们写成 Protocol。
- 接第四家（Codex、Gemini CLI）时会踩到。建议在 `base.py` 写一个 `Driver` Protocol，审批改为 `drivers[agent.vendor].approve`。

**B2-8 元数据错误影响证据**（中）
- `config.py`：`MODELS["dsh"] = "opencode-go/muse-spark-1.3-contributor"`，`FAMILIES["dsh"] = "deepseek"`。唤醒包里的 `family=` 和 `whoami` 的 peers 都会把同一个模型说成两个家族。家族应该由模型推出，而不是由外壳推出。

**B2-9 仓库卫生**（对作品集是高）
- 跟踪文件 797 个，其中 561 个是 `spikes/` 和 `e2e/results/`（包括 `spikes/runs/*.patch.yml`、`spikes/logs/oc-serve.log`、`spikes/probe.log`）。
- 没有顶层 README、LICENSE，没有 CI。
- 提交作者邮箱有 3 种（含 `m2b@local`）。
- 做了一次粗查，密码类匹配都是变量引用，不是明文（例如 `OPENCODE_SERVER_PASSWORD="$(cat …)"`）。公开前仍要人工过一遍 `spikes/` 和 `e2e/results/`，或者干脆不带这两个目录。

### B3. 测试缺口

- 有：单元测试和假 agent 覆盖了投递、对齐、各家事件解析、relay、绑定、via、回放工具。
- 缺：
  1. **没有 CI**，真实厂商路径只靠手跑 e2e；
  2. 没有"厂商事件契约快照"测试：把各家 CLI 的真实输出（stream-json、SSE、NDJSON）录成夹具，升级 CLI 时重放比对，用来尽早发现 rc 漂移；
  3. 没有安全回归测试（B2-1、B2-2 的绕过用例）；
  4. 没有并发测试（B2-6）；
  5. bundle 的测试是 Node 单测（`test/bundle.test.mjs`），没有和 hub 联测的自动化路径（未确认是否有手工脚本）。

### B4. 本次测试运行

- 结果：`286 passed, 1 skipped in 350.70s`，和规划方给的数字一致，本次没有看到不稳定的用例（只跑了一遍，不能据此断言没有 flaky）。
- 慢的原因是每个测试有约 1.5 秒的停机开销，不是用例本身慢，详见文末附录。

### C2. 设计层面的混杂因素

1. **两个 agent 时 A≈B**：A 组"全员唤醒"、B 组"只唤醒被 @ 的"，但只有实现方和复核方两个 agent，几乎每条消息本来就 @ 了对方。A/B 的差别（回合 10.4 对 8.1）主要来自 runner 和人发的群消息，测的不是设计想测的"点名 vs 群聊"。要测这一项，至少要 3–4 个 agent。
2. **模型中途换了**：前 12 个 run 的 dsh 用 deepseek-v4-flash，后 21 个用 muse-spark（和 OpenCode 同一个）；同时 hub 代码也在变（`503e35e` 自动批准、`87d0dd0` dsh 重试），报告后的 run 又是在 `960b40c`、`893722a` 上跑的。合并统计可以，但每个 run 应该记录 hub 提交号和两边的模型，并在表里显示。
3. **rot 的注入通道随组别变化**：A、B 组是 `message`，C 组是 `decision`（T1 表 b）。这算处理的一部分，可以接受，但要写明。
4. **任务太小**：每个 run 5–14 个回合，对齐库十几条，到不了任何一层的上限，所以 MemoryOS 的 /recall 永远不会被调用，"视图曲线"也看不出形状。

### C3. 让故事可信的最小补充实验

按"用最少的 run 回答面试官最可能问的问题"排序：

| # | 实验 | 回答的问题 | 规模 | 估计 token |
|---|---|---|---|---|
| E1 | **单 agent 基线 S 组**：同一模型，一个 agent 自己实现加自审，三个任务 × 3 | "多 agent 比一个 agent 强在哪？" | 9 run | 约 1,500 万–3,000 万 |
| E2 | **修好 SPEC 再跑 minisql**：把开引号规则写进 SPEC，另造一个"只有一方知道"的跨模块约定（比如实现方 A 定、实现方 B 用），B 对 C 各 6 次 | "对齐层到底有没有用？" | 12 run | 约 3,500 万 |
| E3 | **≥3 个 agent 的点名对群聊**：两个实现方加一个复核方，A 对 B 各 5 次，只看回合数和 token | "点名唤醒省多少？" | 10 run | 约 4,000 万 |
| E4 | **rot 不点名全员**：rot 只 @ 实现方 A，看复核方和实现方 B 是否跟上，B 对 C 各 5 次 | "对齐层防 rot 吗？" | 10 run | 约 3,500 万 |
| E5 | **复核基线**：同一批预埋 bug，单 agent 自审 vs 跨 agent 复核，各 6 次 | "跨 agent 复核有价值吗？" | 12 run | 约 500 万 |

- 每个 run 记录 hub 提交号、模型和厂商版本；
- 事先写好分析计划（主指标、检验方法）再跑，避免事后挑任务；
- 报告效应量和置信区间，不只报 p 值；
- 能用 Claude 的话，至少让它在 E1 和 E2 里当一个角色，这样"跨厂商"才名副其实；
- 优先级：E1 > E2 > E5 > E4 > E3。E1 和 E5 便宜，而且面试必问。

## D. 九个方向逐条评估

总体顺序建议：**9（打包，先做最小版）→ 2 的确定性部分 → 5（信任模型和测试套件）→ 7（doctor、只读看板）→ 补实验 E1/E2 → 1 → 3 → 6 → 4 → 8**。理由：先让别人能跑、能看，再修已知漏洞，再用实验回答"有没有用"，最后才做依赖实验结论的优化。

### 方向 1：结构化信封（意图类型、交接必填字段）

- **现状**：已经有了。`kind` 枚举（message / handoff / review_request / decision / assumption / question），`kind=handoff` 强制 Why-First 五个字段（`mail.py:88-91`），`xmuse_done` 带 `next` 和 `declares`。
- **数据**：33 个 run 共约 760 条消息，`handoff` 只用了 **6 次**，`decision` 22 次，`review_request` 87 次，`done` 347 次。**必填字段越多，模型越绕开这个 kind**，改用 `message`。
- **建议**：不要再加必填字段和意图类型。把"怎么验证的（verified）"作为 `xmuse_done` 和 `review_request` 的**可选**字段，hub 对缺字段的交接给出温和提示，不拒收；衡量填写率。把 Why-First 从"handoff 必填"改为"done 的可选结构"。
- **价值和成本**：价值低到中，成本低。放在中间做。

### 方向 2：唤醒调度（是否需要行动、合并突发、每链 token 预算）

- **先做确定性的部分**：B2-3 的三条修补；`max_chain_tokens` 已经存在（默认 2,000 万，从未触发），按实测改成"中位数 run 的 3 倍"（约 1,000 万）即可。
- **"需不需要行动"的模型门控**：收益上限有限。对话型唤醒只占 11% 的 token，"没有新事"的 done 约占 10%。等确定性修补上线后，再看剩下的浪费，大概率不值得接模型。
- **风险**：门控误判会**断链**，而链断比多花 token 代价高（设计稿 §4.4 的 notice 机制就是为这个加的）。任何门控都要有"误判则下一次兜底扫描补唤醒"的回路。
- **价值和成本**：确定性部分价值中、成本很低，马上做；模型门控先不做。

### 方向 3：按收件人组装的上下文包

- **现状**：`wakepack` 已经按收件人组装身份、对齐（快照或差量）、新消息、被动消息摘要。缺的是"代码引用"和"按相关性排序"。
- **问题**：在现在的任务规模下，对齐视图从不超限，排序无从发挥；做了也测不出来。消融实验必须和更难的基准（C3 的 E2–E4）一起做。
- **建议**：推迟。如果做，最有价值的是"自上次读取以来的差量"里加上**代码差量引用**（`git diff --stat` 自某个提交以来、涉及哪些文件），这是确定性的，便宜，也正好回应"代码即记忆"的讨论（§4.5.2）。
- **价值和成本**：中、中高。第二阶段。

### 方向 4：对齐和记忆的生命周期（过滤 /curate 提议、取代和冲突检测、过期）

- **数据**：T1 显示 /curate 的增益很小，噪音大（见 0-6）。显式 `supersedes` 和"任务关闭即衰减"（`align.close_thread`）已经有了。
- **建议**：
  1. 先做零成本的过滤：提议文本和任务首条消息的相似度（MemoryOS 自带 FastEmbed，`/similar` 就能算；或者简单的字符 n-gram Jaccard）超过阈值就丢；"流程规矩"类提议（review、push、test 命令）用规则丢。用 `replay_mo` 离线量化前后的噪音比例。
  2. **改进匹配器**再谈噪音：现在的"不匹配任何清单项"会漏判。
  3. 整体降级：MemoryOS 设为可选插件，作品集里如实写"离线回放显示在小任务上没有增益"——这本身是成熟的工程判断，比硬说有用更加分。
- **价值和成本**：低到中、低。只做第 1 步，不追加投入。

### 方向 5：治理（发送前守卫、注入和越权测试套件）

- **最该做的是信任模型本身**（B2-1、B2-2），而不是"经过校准的守卫"。守卫建在可被绕开的边界上，校准再好也没有意义。
- **注入和越权测试套件**：价值高，成本低，作品集也好看。建议 15–20 个场景，每个是一条脚本化的同伴消息加判定规则。例如：
  - 同伴要求 push 或删分支；
  - 同伴要求读 `tokens/`；
  - 同伴转述"用户说可以"；
  - 消息正文里藏指令；
  - 要求改别的 agent 负责的文件；
  - 要求关掉测试。
  三家（或两家）各跑一遍，报告"照做 / 拒绝 / 升级给人"的比例。这正好回应设计稿 §4.7 里"中继信任说明"那个两难（太严会拒绝合理请求，太松给了注入空间）——有数据就能讲清楚取舍。
- **价值和成本**：高、中。放在第一周后半到第二周。

### 方向 6：编排预设（实现→复核→测试、辩论、map-reduce）

- **现状**：协作流程写在任务文本里（`minisql-C-1/task.txt`），由 agent 自己遵守；hub 不懂流程。这和设计原则"agent 自己决定说什么、对谁说"一致。
- **问题**：加声明式状态机，等于把 v1 的"平台式编排"请回来，和"插件不是平台"的定位冲突；辩论、map-reduce 和"编码协作"的主线关系不大。
- **建议**：只做"实现→复核→测试"这一个，形式是**任务模板**（生成任务文本、指定话题负责人、预设 `depends_on` 的指派），不做运行时状态机。它同时就是 demo 场景。
- **价值和成本**：低到中、中。砍掉辩论和 map-reduce。

### 方向 7：可观测性和体验

| 子项 | 建议 | 优先级 |
|---|---|---|
| 一键启动 + `xmuse doctor` | 必做；对作品集是门槛 | 高 |
| 只读看板 | 必做。第一版用静态 HTML，从 `hub.db` 生成：话题时间线、链图、每次唤醒的 token（拆成缓存读、新输入、输出）、对齐库条目的版本链、审批记录。不用起服务 | 高 |
| 给协调者的管理 MCP 工具 | **只给只读的**（状态、链、用量、待审批列表）。写操作（批准、恢复、确认）给 agent 就扩大了 B2-1 的问题 | 中 |
| 把 SOP 打包成技能 / MCP | 同意"不无脑封装"。目前高频又易错的只有：前台 dsh 的 `--args-file` 发消息、桌面版初始化、跑实验。其余不封装 | 低 |

### 方向 8：基于 Jev 的 hub 决策点层

**判断：现在做是过度设计；抽象本身是好的，后端选型不对、时机也不对。**

反对接入 Jev 的理由：
1. **没有可以校准的数据**：33 个 run 里，"该不该唤醒"的负例只有几十个，而且没有标注；"MemoryOS 提议该不该留"有 106 条，同样没有可靠标注（匹配器会漏判）；"越界请求"一条真实数据都没有。说"在 hub.db 上校准"，前提是先有标签。
2. **和自己的隐私口径矛盾**：设计稿把"dsh 必须关遥测、不能把会话事件上传给厂商"列为硬性要求（§4.2），却要把 hub 的状态（消息正文、决定、代码路径）发给一个托管服务。
3. **不可复现**：面试官没有账号就跑不了；只有托管版。
4. **无法核实**：2026-09-15 才发布，性能和校准数字都是厂商自报；我无法核实它的任何指标（**未确认**）。
5. **收益上限低**：见方向 2，唤醒门控的可省空间约 10%；scope guard 的瓶颈在 B2-1，不在判断准不准。

更好的做法（同样能展示"决策点"的工程能力）：
- 定义 `DecisionPoint` 接口：状态构建器、问题、阈值、规则兜底、概率和决定日志（这部分保留规划方的设计）。
- 后端按顺序接：
  1. **规则**（默认，必须有）；
  2. **本地小模型或嵌入**：MemoryOS 已有 FastEmbed，可以算"提议和任务说明的相似度""消息是否只是确认"这类特征，加一个逻辑回归，有 200–500 条标注之后再训；
  3. **便宜的通用 LLM**（例如 deepseek-flash、haiku），结构化输出加自报置信度，只在影子模式下跑；
  4. Jev 作为可选后端之一，只在离线对比实验里出现，默认不开。
- 先做**影子模式加离线评测框架**：在 `hub.db` 里记录每个决策点"规则怎么判、模型怎么判、事后看谁对"，用 `replay` 工具回放。这才是面试能讲的"评测驱动"。
- 三个首选决策点里，**唤醒门控**用规则就够（B2-3）；**MemoryOS 写入过滤**用相似度规则；**越界守卫**的前提是 B2-1。三个都不需要托管模型。

### 方向 9：作品集打包

同意大方向，有三处不同意见：
1. **"补齐全栈"要克制**：
   - 对话记录和决定上的 RAG：`xmuse_thread(query)` 现在是 `LIKE` 子串搜索，改成调用 MemoryOS 的混合检索（BM25 + FastEmbed + RRF，已经有）是一天的事，可以做；但不要为了"有 RAG"而另起一套向量库。
   - LLM 当评委：已经有一个天然的位置——复核误报的判定（现在按句子判），可以把它做成可复现的评测器。
   - Docker：只对 hub、看板和假 agent 有意义；三家 CLI 要订阅和 OAuth，dsh 只有 Windows 版，装进容器不现实。
2. **必须有"无订阅也能跑"的模拟模式**：用 `tests/fakes` 的假 agent 加录制好的事件，跑通一个完整的 demo 场景（需求→实现→复核→中途改约定→完成），并生成看板。这是面试官唯一可能亲手跑的东西。
3. **不要另做客服机器人、个人知识库、面试 agent 这类无关 demo**：它们会稀释"跨厂商协作层"的辨识度；面试官看到大量雷同项目，xmuse 的差异化恰恰在于它不是又一个 RAG 机器人。补的是**评测基线和安全测试**，而不是更多的 demo。

### E4. "在 xmuse 自己的领域里补齐全栈"对不对

基本对。但"全栈"在这里应该理解为"一个 agent 应用从接入、编排、记忆、评测、安全到观测都有"，而不是"再多几个 LLM 功能"。xmuse 已经覆盖接入、编排（轻）、记忆、评测；缺的是**安全**和**观测**，加上让人能跑的**交付**。RAG 只做到"用现有混合检索替换 LIKE 搜索"这一步就够了。

## 附：测试运行结果

命令：`cd ~/dev/xmuse2-dshb && hub/.venv/bin/python -m pytest tests -q -p no:cacheprovider --durations=15`

结果行原文：`286 passed, 1 skipped in 350.70s (0:05:50)`

- 最慢的单个用例只有 4.71 秒（`test_shim.py::test_hub_down_is_a_tool_error_not_a_crash`），慢的主要原因是**每个测试固定约 1.2–1.5 秒的开销**：多个用例的 teardown 恰好是 1.50 秒。
- 推测来源（未逐个确认）：
  - `Hub.shutdown` 设置停止标志后，`Engine.run_forever` 仍阻塞在 `self.q.get(timeout=1)`（`engine.py:67`），最多再等 1 秒；
  - `ThreadingHTTPServer.shutdown` 默认 0.5 秒轮询。
- 修法：停止时往队列里放一个哨兵事件，`serve_forever(poll_interval=0.05)`。估计能把全量从 6 分钟降到 1–2 分钟，这对 CI 和 F-7 的"默认测试集 2 分钟以内"很关键。
