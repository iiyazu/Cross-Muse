# T16 协作层实验设计（草案，2026-10-12，base 起草，待用户定）

## 0. 为什么停掉 T15 团队系列
T15 的拓扑和题目几乎不需要协作，所以信息层开与不开，结果只会落在噪声里：
- **题目**：70 个 bug 都是单文件替换。"跨层"只是说症状跨层，修复本身只动一个文件。按文件分工以后，每个 bug 只归一个人。r3、r4 的整合后分数正好是两人之和（19+28、17+21），没有重复、没有丢失、没有冲突。协作类指标在两组里都会是 0。
- **信息无人消费**：r4 里 dsh-fl 写了 4 条假设和决定，但 P1 是两人并行隔离干活，P2 规划者只检查编译和文件归属，没有任何环节去读这些条目。
- **反馈环断了**：条件是只能推理。规划者看不到失败，r4 就直接 `next: none` 收尾，修复轮从未发生。
- **噪声大**：每组只有 3 次，同一个执行者在不同 run 之间产出差距很大。

## 1. 要测的是什么：信息层的四个机制 → 四个假设
| 机制（只有 info_layer=on 才有） | 在什么场景下有价值 | 假设 |
|---|---|---|
| 条目持久化并注入每次唤醒（decision、assumption） | agent 经常开新会话，前面定下的约定必须延续下去 | H1：多轮新会话之后，xmuse 组违反早先约定的次数更少 |
| question 的 resolves 答复关系、依赖等待和唤醒 | 一方缺的事实只有另一方知道 | H2：xmuse 组跨归属的问题被答复的比例更高、更快，而且答复确实被用上 |
| supersedes（取代旧条目） | 中途改需求，旧约定作废 | H3：需求变更后，xmuse 组两侧都按新约定改的比例更高 |
| scope 路由、assignment 分派 | 失败要准确派回对应的归属方 | H4：xmuse 组派错人、没人认领的失败更少，修复轮的净增益更高 |

## 2. 题目：猎场 v3 的要求（只定性质；bug 定义由谁来写由用户决定，见第 7 节）
1. **耦合对（主体，建议 ≥ 20 对）**：一对 bug 分别在两个执行者的归属文件里，比如生产方写的键格式和消费方读的键格式、枚举里用 code 还是 desc、金额单位。只修一侧不得分；判定测试检查的是两侧是否一致，而且必须符合唯一正确的约定。
2. **证据分布**：正确约定的证据（schema、fixture、注释、调用方）放在某一方的归属区域里，另一方要靠提问或者对方主动告知才能知道。注意：证据不能只出现在双方都会读的公共文件里，否则就不需要交流。
3. **中途需求变更（2–3 条）**：第 3 轮开始时，hub 以"产品负责人"的身份发一条固定消息，改掉某个约定，比如某个状态码的取值。判定测试按变更后的约定来写。两组收到的消息文本、发出时刻完全相同。
4. **独立 bug（保留 20–30 个）**：用来对照，看个人推理能力；这部分预期两组没有差别。
5. 照旧做验证：干净树全过；全注入后可见测试通过、判定测试失败；逐个不遮蔽；参考解满分；原样猎场 0 分。耦合对另外要验证：只修一侧时判定测试仍然失败。

## 3. 拓扑：契约中继（新预设，暂名 `contract-relay`）
- **角色**：
  - P 是架构师兼集成者，不写功能代码；拥有"契约"，也就是约定的最终决定权；只有 P 能在集成后的主线上跑可见测试（每轮限 1 次）。
  - E1 负责 domain + trigger。
  - E2 负责 infrastructure + mapper + app 配置。
  - 按层分工，正是为了让耦合对跨在两人之间。
- **节奏**：30 分钟分成 P0（4 分钟）加 6 个短轮（每轮约 4 分钟）。每一轮的流程是：执行者干活 → hub 合并 → P 跑测试、把失败派回对应的人 → 下一轮。
- **每轮执行者都开新会话**（fresh）。旧上下文不带过去，只能靠 hub 的唤醒包：xmuse 组的唤醒包里有全部有效条目；plain 组只有自上次以来的新消息。这一点正是用来检验 H1 的。
- **执行者只能推理和编译**，保持 T15 的 5b 条件；只有 P 能看到测试结果。这是团队里唯一的反馈来源，所以失败信息必须靠通信传过去。
- **第 3 轮开始时发需求变更消息**（第 2 节第 3 条）。
- **两组唯一的差别是 info_layer**。题面、时限、模型、预设参数完全相同。

## 4. 指标
**主要**（事先指定，只看这三个）：
1. 耦合对一致修好率（两侧都按正确约定改了的对数 / 总对数）；
2. 需求变更遵守率（变更涉及的点里，最终按新约定实现的比例）；
3. 最终修好数 F。

**过程指标**：
- 跨归属提问的次数、被答复的比例、答复耗时；
- 违反早先约定的次数（判定器按约定逐点检查）；
- 失败派对人的比例；
- 每一轮的净增益；
- token 和用时；
- 两组各自的消息数、条目数。

**操纵检查**（不满足就不进入正式实验）：
- 每个 run 至少有 N 次跨归属的信息交换（建议 N = 5），两组都要满足；
- 修复轮确实发生了（≥ 3 轮）。

## 5. 次数与流程
1. **试跑**：plain 和 xmuse 各 1 次，只看操纵检查和机制是否真的被用到，不看分数。不满足就改题目或拓扑，再试跑。
2. **正式实验**：每组 6 次，plain 和 xmuse 交替进行。开跑前提交预注册。
3. **隔离**：每个 run 跑完后，工作区移出 C:，每次都做跨 run 读取扫描（T15 的教训）。另外，"证据只在一方"能不能成立，取决于 agent 能不能直接读对方的文件：现在 dsh 可以读整个盘，所以对方的 worktree 也读得到。要真正做到信息不对称，需要按槽位建 Windows 用户 + bwrap（见 T15 第 12 步之后的讨论）。如果不做隔离，第 2 节第 2 条只是增加了"自己去找"的成本，而 H2 测到的是"问比自己去找更划算"。

## 6. 实现范围
- **hub**：新预设 `contract-relay`（多轮循环、每轮执行者新会话、P 的测试结果路由给对应的人、固定时刻注入需求变更），放在 `preset.py`，再写测试。
- **kit**：
  - bench-tests MCP：P 用的版本有 `run_tests`（只跑可见测试，每轮限 1 次），执行者用的版本仍然只有 `compile`；
  - 判定器：增加耦合对和需求变更的计分；
  - `team_run`、`team_report`：增加新指标和操纵检查。
- **猎场 v3**：bug 定义 + 判定测试 + 验证（按第 2 节）。
- **可选**：多用户 + bwrap 隔离（第 5 节第 3 条）。

## 7. 需要用户定
1. **P 能不能跑可见测试**（只有 P 能跑，每轮 1 次）？这会部分放松"只推理"，但只有放开它，修复轮才会真正发生、失败派发才有意义。
2. **猎场 v3 的耦合对和需求变更由谁来写**：r7、另一个会话，还是 base？上一次写更难版本的猎场时，base 的设计回复被安全检查拦了，所以不默认由 base 来写。base 负责合并、验证、写判定器和预设。
3. **每轮执行者都开新会话**，可以接受吗？
4. **做不做多用户 + bwrap 隔离**：做了才是真正的信息不对称，也可以支持并行跑。
5. **T15 已有的数据怎么处理**：建议写成"低协作需求下的基线和开销测量"，不做两组对比。
