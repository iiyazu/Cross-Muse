# xmuse 2 下一个里程碑：协作拓扑功能（草稿，待用户审）

2026-10-12，r7 coord。前提：
- 探针已经给出"协作层有用"的证据，实验交给另一个会话收尾（`HANDOFF-BASE-REPORT` 的"T17 收尾工单"）。
- 这个里程碑转做功能。用户 10-12 定了原则：xmuse 聚合的是本来就有各自特色的 agent，要什么能力就接入本来具备它的 agent，不改造 Claude 或 OpenCode。所以"常驻成员"不在本里程碑做，聚合新 agent（比如 Hermes）排在最后。

每个功能的做法：
- **配一个小探针**，和 S 系列一样小而确定，验证"做了以后确实有用"，不再单独开评测。
- **侧栏能看到、能操作**。
- **合 main 前问用户。**

## 范围和顺序

| T3 | 私信分享走审批，规则给建议 | 小 | 用户 10-12 定的规则：正式使用时私信默认不外传 |

## T0 易用性：加人、组织、主控分派

**用户的决定**（10-12，对照 Grok Bot 时定的）：
1. **本机加入不再要邀请码**。用户在侧栏里点一下就是授权；agent 自己不能加入任何房间。邀请码只留给以后可能出现的远程或多用户场景。
2. **主控负责接活和分派**。用户不点名的话，默认交给主控，由它分析后派给别人干。这是用户做 xmuse 的初衷之一：智能高的 Claude 额度珍贵，Claude 负责接活和分析，其他成员负责干活。

**现状**：
- 消息拓扑已经是自由的：任何成员都能私聊任何人，也能直接建 `#群`。
- `transfer_host` 已经有了。
- 缺的是：
  - 侧栏的 act 里没有"加成员"，hub 能自己起的成员只能用命令行 `xmuse agent add` 加；
  - 加入一律要邀请码（XXXX-XX，10 分钟有效）；
  - 角色和描述加入后改不了；
  - 主控只代表"谁开的房间"，对消息路由没有影响。

### 加人：两种成员，两种加法

- **hub 能自己起的**（OpenCode，以及 Claude Code、dsh 的命令行模式）：在侧栏点"添加成员"，选厂商、模型、角色、描述，hub 立刻登记，下次有消息就起回合。
  - 新增 `act member_add {vendor, model, role, description, name?}`，只有操作令牌能调；
  - 等同于 `xmuse agent add`。
- **用户正开着的窗口**（Claude 桌面版、OpenCode TUI、dsh 前台）：
  - **同目录**：房间就是这个目录，侧栏启动时从 `.xmuse.json` 和状态目录里的 `hub.json` 发现本目录的 hub，提示"加入 <房间名>？"，点一下就加入。
  - **跨目录**：hub 启动时写进本机登记表 `%LOCALAPPDATA%\\xmuse\\hubs.json`（Linux 下是 `$XDG_STATE_HOME/xmuse/hubs.json`），内容是房间名、目录、地址、主控、在线状态，退出时删除。侧栏的"房间"页列出本机所有房间，点选加入。
  - **加入接口**：`POST /v1/join` 改成接受 `{dir 或 room_id, vendor, session_id, name?, role?, description?}`，不再要求 `code`。
  - **鉴权**：hub 只在请求来自本机回环地址、并且带上侧栏插件的本机凭据时才接受。凭据是一个"侧栏令牌"文件，只放在用户目录下，权限 600；agent 的进程环境里不带它，各家插件读它。
  - **邀请码保留**，但只在远程场景（以后才有）启用，默认关闭。
- **安全底线**：
  - 成员令牌（agent 用的）调 join、member_add 一律 403；
  - `xmuse_*` 工具里不提供加入或加人的功能；
  - 加入和加人都记进 `#room` 事件，侧栏可见。

### 组织：右键菜单和小群（原 T2）

- **成员列表右键**：
  - 设为主控（`transfer_host`）；
  - 改角色和描述（新增 `act member_edit {member, role?, description?}`）；
  - 暂停、恢复、移出（已有）；
  - 私聊（打开 `dm:` 线程）；
  - 拉进群。
- **线程列表**：私聊和群聊并列；"新建群聊"可以勾选成员。小群的具体设计见下面 T2。
- **团队模板**（可选，T0 末尾）：一键建"主控 Claude 加两个执行者加一个审查者"这类阵容，复用 `preset.py` 的 plan-split-integrate 角色。

### 主控分派：让 Claude 只花在接活和分析上

- **用户不点名的话交给主控**：用户在侧栏或命令行里说话时，如果没写 `to`，或者写到 `#room`、`#team` 却没点名，hub 只唤醒主控，其他成员只收被动投递。主控的唤醒包里注明"用户的新任务，你是主控：先分析，再用 handoff 派给合适的成员"。
- **主控的提示要求**：分析、拆分、分派、验收；自己不动手写代码，除非用户点名要它做。写进主控的身份段，不改 Claude 本身，只是 xmuse 给它的角色说明。
- **少唤醒主控**：这是省 Claude 额度的关键。做法是给结果回传加分类标签（用户 10-12 提出），按标签决定唤醒方式。
  - 执行者结束时在 `xmuse_done` 里填 `outcome`：

    | 标签 | 含义 | 对主控 |
    |---|---|---|
    | `completed` 正常完成 | 任务按要求做完，没有新约定 | **按批次等**：这一批派出的任务全部交回，或者到上限（默认 10 分钟），合并成一次唤醒 |
    | `needs_alignment` 需要对齐 | 发现需要主控或别人定的事：接口或约定要改、和现有决定冲突、做出了会影响别人的假设 | **立即唤醒** |
    | `blocked` 卡住或失败 | 做不下去，或者验收没过 | **立即唤醒** |
    | `progress` 进展 | 中间汇报，还没完成 | 不唤醒，只被动投递 |

    提问照旧走 `kind: question`，立即唤醒。
  - **hub 兜底，不全靠执行者自觉**：
    - 标了 `completed`，但 `declares` 里带了 decision、assumption、question，而且 scope 不只是自己，或者 supersedes 了现有条目——hub 自动改判为 `needs_alignment`；
    - T5 的证据核对不通过——hub 自动改判为 `blocked`。
    - 改判记在消息上，侧栏可见；各成员的标签分布和被改判的次数也在侧栏显示，用户能看出谁在乱标。
  - 主控派活时，也可以给单个任务标"交回立即叫我"，用于后续分派要看这个结果的情况。
  - 侧栏显示"主控在等哪几个任务"，可以手动"现在叫醒主控"。
- **和 T5 联动**：执行者的 done 带证据并经 hub 核对过，主控就不用花 token 重新检查。
- **度量**：在侧栏的成员卡片和 `xmuse log` 里单独列出主控的 token 和唤醒次数，让用户看到"Claude 花在了哪里"。

### 探针

1. **加人路径**（产品验收，不是实验）：从空房间开始，用侧栏完成以下操作，统计用户动作数和用时，目标是每步一次点击：
   - 加两个 hub 起的成员；
   - 把一个开着的 OpenCode TUI 拉进来；
   - 设主控；
   - 建一个三人小群。
2. **主控分派**（tick 或 R 世界）：用户只对房间说任务，不点名；主控是 Claude（haiku 做探针），另有两个执行者。判定：
   - 任务完成；
   - 主控的 token 占全队的比例：对照组是"用户直接把任务交给 Claude 让它自己做完"，以及"每个执行者更新都唤醒主控"；
   - 主控被唤醒的次数。

   这个探针直接回答用户初衷里的问题：Claude 是不是只花在了接活和分析上。

## T1 唤醒包开销：先量再剪

**现状**：唤醒包依次是 relay 说明、身份、对齐区（新会话给快照，之后给增量）、消息、被动摘要。对齐区平时只是增量，所以 S1 里 X 多出来的那 15% 未必来自对齐区。`4978d60` 之后每个唤醒包都存成了 `runs/turn-N.pack.md`，可以直接量。

**做法**：
1. **量**：
   - 用 batch1 里 S1、S2、DEP 的包，按段统计 X 组和 P 组每次唤醒的 token：relay 说明、身份、对齐快照、对齐增量、消息、被动摘要；
   - 再和回合日志里的输入 token 对照，看包本身占多少，后续回合的工具调用又占多少；
   - 结果写成一张表。
2. **剪**：只剪大头。候选：
   - relay 说明和身份是不是每次都要全文，同一会话里第二次以后可以只给一行；
   - 增量为空时省掉整个标题；
   - 被动摘要的长度上限。

   每项单独提交，带测试。

**探针**：
- S1 X 组和 S2 X 组各跑 5 次（seed 11–15），主要指标必须保持不变（都是 0）；
- 整个 run 的 token 和 batch1 的 X 组、P-bc 组比，目标是不高于 P-bc。

**侧栏**：成员卡片上已有 `tokens_hour`，不改。

## T2 线程成员：小群

**现状**：往 `#名字` 发第一条消息时，hub 自动建线程并加入全部成员和用户，没有"只拉几个人"的办法。加入已有条目的线程时会补发快照，这部分已经有了。

**设计**：
- 建线程时可以带成员名单：
  - 成员用 `xmuse_send` 的 `to: "#名字"`，加 `members: [...]`，只在第一次建线程时有效；
  - 用户在侧栏用 `act` 新增 `thread_new {id, members}`。

  不带名单时照旧拉全员，保持兼容。
- 线程成员的增减：
  - 用户在侧栏操作：`act thread_add {id, member}`、`thread_remove`；
  - 成员只能把自己加进公开线程，或者退出线程。
- 非成员收不到这个线程的投递（不唤醒，也没有被动投递），`xmuse_thread` 读不到它的内容。对齐条目的 scope 是 `thread:#x` 时，只进成员的对齐区。
- 侧栏视图的 `threads[].members` 已经有了，补上建线程和加减人的操作；约定 v0.1 加这三个 act。

**探针**（tick 世界，3 个成员）：
- `#ab` 只有 a、b，`#team` 是全员；
- 前段在 `#ab` 里定一条只和 a、b 有关的规则，中途把 c 加进 `#ab`，c 之后也要遵守；
- 判定：
  - 加入前 c 的唤醒包里没有 `#ab` 的内容，c 的 token 对比"全在 `#team` 说"的对照组；
  - 加入后 c 照做的比例。

## T3 私信分享走审批，规则给建议

**规则**（用户 10-12）：正式使用时，用户私信给某个成员的内容默认不外传，要分享得用户主动批准。实验里需要的话可以在场景里写明默认可分享。

**设计**：
- 审批队列新增 `kind: "share"`：
  - 成员调用 `xmuse_share {message_id, to, why}`，只能分享自己收到的、来自用户的私信；
  - 用户在侧栏选"批准一次 / 以后都可以 / 拒绝"。"以后都可以"只放行这一条消息分享给这个对象，不放行这个对象以后的所有分享；
  - 批准后，hub 把原文作为 `via: shared` 投给目标，并注明出处。
- 用户也可以在侧栏把某条私信直接标成"可分享"，等于预先批准。
- **建议**（决策点，只建议不执行，先用规则）：队友发 question、或者被分派任务时，如果提问或任务里出现了某条用户私信里的键名或关键词，就提示收到这条私信的成员"你有一条私信可能相关，可以申请分享"。

  按审计（方向 8）的结论：后端先用规则，再用本地 FastEmbed，Jev 只在离线对比里出现。

**探针**：用 S3b 的世界，但 k 不写"可分享"。
- 判定一：没有批准时，k 不出现在 e1 的任何唤醒包里，目标 10/10。
- 判定二：脚本里的用户批准后，e 正确的比例。
- 另记建议的触发次数，以及触发对不对。

## T4 按职责描述路由提问

**现状**：成员能看到队友的职责描述（`whoami.peers[].description`），S3b 里三组几乎都能找对人。人多以后，在 `#team` 里不点名地发 question，会唤醒所有人。

**设计**：
- 发 `kind: question` 却没点名时，hub 拿问题文本和各成员的职责描述做规则匹配（关键词，之后可以换成 FastEmbed）；
- 只唤醒最匹配的 1–2 个成员，其他人只收被动投递，并在投递里注明"按职责描述路由给 X"；
- 匹配不上时照旧唤醒所有人。

**探针**：6 个成员，各有不同的职责描述，`#team` 里依次发 5 个不点名的问题。判定：
- 第一次被唤醒的就是答题者的比例；
- 每个问题的唤醒次数和 token。

对照组是"不路由、全员唤醒"。

## T5 用证据判断完成

**现状**：`xmuse_done` 只有 `summary`、`next`、`declares`、`stage` 四项，"做完了"没有任何依据。

**设计**：
- `xmuse_done` 加可选字段 `evidence: [{kind: "test" | "diff" | "command", ref, result}]`。
- hub 拿回合日志核对（转录里有工具调用）：
  - 声称跑过的测试命令，确实出现在这个回合里，而且退出码对得上；
  - 声称改过的文件，确实有写入。

  对不上的，在 done 消息上标注"未核实"，侧栏显示出来。
- 可选：房间里有审查者角色时，done 声明 `next: none`，hub 先把它交给审查者核验，审查者 done 之后才算完成（R6 已经搭出这个形态）。

**探针**：R 世界的小项目里埋一个"看起来过了、其实没过"的测试陷阱。判定：
- "错误的完成"被接受的比例：没有证据要求时对比有证据要求时；
- 审查者核验带来的额外 token。

## T6（最后）聚合新 agent

- 用户定的方向：常驻、personal agent 一类的能力，靠接入本来就具备它的 agent，例如 Hermes，不改造 Claude 或 OpenCode。
- 已查明的接入方式：Hermes 支持第三方"消息平台插件"，放在 `~/.hermes/plugins/<名>/`，包含 `plugin.yaml` 和继承 `BasePlatformAdapter` 的 `adapter.py`，**不改 Hermes 核心代码**。xmuse 可以作为 Hermes 的一个平台，插件通过 D2 的视图接口长轮询拿到点名它的消息，再用 `act say` 回话。这样 Hermes 自己的常驻、定时任务和记忆都保留。参考文档：`~/.hermes/hermes-agent/gateway/platforms/ADDING_A_PLATFORM.md`。
- 本里程碑不做，等 T1–T5 完成后再定。

## 分工建议

- hub 部分（T1–T5 的服务端、工具、约定 v0.1）：派 Sonnet 子代理，在各自的工作树里做，coord 审查、合 rc。
- 侧栏部分（各家的建线程、加减人、share 审批、"未核实"标记）：交给开发房间里待命的 oc-d4、dsh-d4。
- 探针：交给实验会话收尾之后，或者由子代理照 S 系列的执行器扩展。
- 约定：每项功能先改 `XMUSE2-VIEW-API.zh.md`，出 v0.1，再动侧栏。

## 已定（用户 10-12）

- 本机加入不要邀请码，侧栏点击即授权，agent 不能自行加入。
- 主控负责接活和分派：Claude 额度珍贵，Claude 接活分析，其他成员干活。

- 顺序：T0 → T1 → T5 → T3 → T4。
- 成员可以自己建私有小群（带成员名单），用户在侧栏可以加人、减人。
- T5 的审查者核验：正式使用时默认开。测试场景按具体测试选，选不会干扰该测试的那一边，并在预注册里写明。

- 主控唤醒按结果标签区分：正常完成按批次等，需要对齐、卡住、提问立即唤醒；hub 根据 declares 和证据核对结果兜底改判（用户 10-12 提出标签，r7 补全了分类和兜底规则）。
