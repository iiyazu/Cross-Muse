# xmuse 2 下一个里程碑：协作拓扑功能（草稿，待用户审）

2026-10-12，r7 coord。前提：
- 探针已经给出"协作层有用"的证据，实验交给另一个会话收尾（`HANDOFF-BASE-REPORT` 的"T17 收尾工单"）。
- 这个里程碑转做功能。用户 10-12 定了原则：xmuse 聚合的是本来就有各自特色的 agent，要什么能力就接入本来具备它的 agent，不改造 Claude 或 OpenCode。所以"常驻成员"不在本里程碑做，聚合新 agent（比如 Hermes）排在最后。

每个功能的做法：
- **配一个小探针**，和 S 系列一样小而确定，验证"做了以后确实有用"，不再单独开评测。
- **侧栏能看到、能操作**。
- **合 main 前问用户。**

## 范围和顺序

| T1 | 唤醒包开销：先量再剪 | 小 | S1 发现，整个 run 里 X 比群发多约 15% token，直接影响"用 xmuse 划不划算"；先量清楚再动，风险低 |
| T2 | 线程成员：小群 | 中 | 拓扑的基础；现在 `#名字` 一建就拉全员，开放群聊费 token |

## T1 唤醒包开销：先量再剪

**现状**：唤醒包依次是 relay 说明、身份、对齐区（新会话给快照，之后给增量）、消息、被动摘要。对齐区平时只是增量，所以 S1 里 X 多出来的那 15% 未必来自对齐区。`4978d60` 之后每个唤醒包都存成了 `runs/turn-N.pack.md`，可以直接量。

**做法**：
1. **量**：
   - 用 batch1 里 S1、S2、DEP 的包，按段统计 X 组和 P 组每次唤醒的 token：relay 说明、身份、对齐快照、对齐增量、消息、被动摘要；
   - 再和回合日志里的输入 token 对照，看包本身占多少，后续回合的工具调用又占多少；
   - 结果写成一张表。
2. **剪**：只剪大头。候选：
   - relay 说明和身份是不是每次都要全文，同一会话里第二次以后可以只给一行；
   - 增量为空时省掉整个标题；
   - 被动摘要的长度上限。

   每项单独提交，带测试。

**探针**：
- S1 X 组和 S2 X 组各跑 5 次（seed 11–15），主要指标必须保持不变（都是 0）；
- 整个 run 的 token 和 batch1 的 X 组、P-bc 组比，目标是不高于 P-bc。

**侧栏**：成员卡片上已有 `tokens_hour`，不改。

## T2 线程成员：小群

**现状**：往 `#名字` 发第一条消息时，hub 自动建线程并加入全部成员和用户，没有"只拉几个人"的办法。加入已有条目的线程时会补发快照，这部分已经有了。

**设计**：
- 建线程时可以带成员名单：
  - 成员用 `xmuse_send` 的 `to: "#名字"`，加 `members: [...]`，只在第一次建线程时有效；
  - 用户在侧栏用 `act` 新增 `thread_new {id, members}`。

  不带名单时照旧拉全员，保持兼容。
- 线程成员的增减：
  - 用户在侧栏操作：`act thread_add {id, member}`、`thread_remove`；
  - 成员只能把自己加进公开线程，或者退出线程。
- 非成员收不到这个线程的投递（不唤醒，也没有被动投递），`xmuse_thread` 读不到它的内容。对齐条目的 scope 是 `thread:#x` 时，只进成员的对齐区。
- 侧栏视图的 `threads[].members` 已经有了，补上建线程和加减人的操作；约定 v0.1 加这三个 act。

**探针**（tick 世界，3 个成员）：
- `#ab` 只有 a、b，`#team` 是全员；
- 前段在 `#ab` 里定一条只和 a、b 有关的规则，中途把 c 加进 `#ab`，c 之后也要遵守；
- 判定：
  - 加入前 c 的唤醒包里没有 `#ab` 的内容，c 的 token 对比"全在 `#team` 说"的对照组；
  - 加入后 c 照做的比例。

## T3 私信分享走审批，规则给建议

**规则**（用户 10-12）：正式使用时，用户私信给某个成员的内容默认不外传，要分享得用户主动批准。实验里需要的话可以在场景里写明默认可分享。

**设计**：
- 审批队列新增 `kind: "share"`：
  - 成员调用 `xmuse_share {message_id, to, why}`，只能分享自己收到的、来自用户的私信；
  - 用户在侧栏选"批准一次 / 以后都可以 / 拒绝"。"以后都可以"只放行这一条消息分享给这个对象，不放行这个对象以后的所有分享；
  - 批准后，hub 把原文作为 `via: shared` 投给目标，并注明出处。
- 用户也可以在侧栏把某条私信直接标成"可分享"，等于预先批准。
- **建议**（决策点，只建议不执行，先用规则）：队友发 question、或者被分派任务时，如果提问或任务里出现了某条用户私信里的键名或关键词，就提示收到这条私信的成员"你有一条私信可能相关，可以申请分享"。

  按审计（方向 8）的结论：后端先用规则，再用本地 FastEmbed，Jev 只在离线对比里出现。

**探针**：用 S3b 的世界，但 k 不写"可分享"。
- 判定一：没有批准时，k 不出现在 e1 的任何唤醒包里，目标 10/10。
- 判定二：脚本里的用户批准后，e 正确的比例。
- 另记建议的触发次数，以及触发对不对。

## T4 按职责描述路由提问

**现状**：成员能看到队友的职责描述（`whoami.peers[].description`），S3b 里三组几乎都能找对人。人多以后，在 `#team` 里不点名地发 question，会唤醒所有人。

**设计**：
- 发 `kind: question` 却没点名时，hub 拿问题文本和各成员的职责描述做规则匹配（关键词，之后可以换成 FastEmbed）；
- 只唤醒最匹配的 1–2 个成员，其他人只收被动投递，并在投递里注明"按职责描述路由给 X"；
- 匹配不上时照旧唤醒所有人。

**探针**：6 个成员，各有不同的职责描述，`#team` 里依次发 5 个不点名的问题。判定：
- 第一次被唤醒的就是答题者的比例；
- 每个问题的唤醒次数和 token。

对照组是"不路由、全员唤醒"。

## T5 用证据判断完成

**现状**：`xmuse_done` 只有 `summary`、`next`、`declares`、`stage` 四项，"做完了"没有任何依据。

**设计**：
- `xmuse_done` 加可选字段 `evidence: [{kind: "test" | "diff" | "command", ref, result}]`。
- hub 拿回合日志核对（转录里有工具调用）：
  - 声称跑过的测试命令，确实出现在这个回合里，而且退出码对得上；
  - 声称改过的文件，确实有写入。

  对不上的，在 done 消息上标注"未核实"，侧栏显示出来。
- 可选：房间里有审查者角色时，done 声明 `next: none`，hub 先把它交给审查者核验，审查者 done 之后才算完成（R6 已经搭出这个形态）。

**探针**：R 世界的小项目里埋一个"看起来过了、其实没过"的测试陷阱。判定：
- "错误的完成"被接受的比例：没有证据要求时对比有证据要求时；
- 审查者核验带来的额外 token。

## T6（最后）聚合新 agent

- 用户定的方向：常驻、personal agent 一类的能力，靠接入本来就具备它的 agent，例如 Hermes，不改造 Claude 或 OpenCode。
- 已查明的接入方式：Hermes 支持第三方"消息平台插件"，放在 `~/.hermes/plugins/<名>/`，包含 `plugin.yaml` 和继承 `BasePlatformAdapter` 的 `adapter.py`，**不改 Hermes 核心代码**。xmuse 可以作为 Hermes 的一个平台，插件通过 D2 的视图接口长轮询拿到点名它的消息，再用 `act say` 回话。这样 Hermes 自己的常驻、定时任务和记忆都保留。参考文档：`~/.hermes/hermes-agent/gateway/platforms/ADDING_A_PLATFORM.md`。
- 本里程碑不做，等 T1–T5 完成后再定。
