# xmuse 2 侧栏方案设计稿（草稿，等用户审阅）

2026-10-11，r7。第二版：不做独立 exe，也不做单独的网页面板。xmuse 只以各家桌面端里的**侧栏**出现：开房间的那一家当主控，其他成员的侧栏同样能看到全部信息、做审批。

## 1. 已定（用户 10-11）

| 项 | 决定 |
|---|---|
| 形态 | 不做独立 exe，不做网页面板；为每个支持 xmuse 的 provider 做侧栏 |
| 主控 | 在哪一家的侧栏里开房间，那一家就是这个房间的主控，承担原来 exe 的职能（开房间、邀请、成员管理） |
| 其他成员的侧栏 | 能看到全部信息，也能审批 |
| hub 运行位置 | Windows 原生（不再依赖 WSL） |
| agent 单独 OS 用户 | 暂时搁置（安全模型里如实写明缺口） |

## 2. 用户流程

1. 用户在任意一家（例如 Claude 桌面版）打开 xmuse 侧栏，点"开房间"，选工作目录、起名。这一家的这个会话成为**主控**，它自己也是房间里的一个成员。
2. 主控侧栏里点"邀请"，选 provider（Claude / OpenCode / dsh）和角色，得到一次性邀请码（10 分钟过期，只能用一次）和一条可以复制的命令，如 `/xmuse join K7Q2-9F`。
3. 用户在**想要的那个会话**里执行这条命令（或在那家侧栏里点"加入"并粘贴邀请码）。插件把"邀请码 + 本会话 id"交给 hub，绑定完成，所有侧栏上这个成员变成"在线"。
4. 之后：用户在任一侧栏或会话里 @ 某个成员，hub 负责投递和唤醒；被 @ 的 agent 在自己的原生界面里看到消息并处理。每个侧栏都显示整个房间的时间线。
5. 审批（OpenCode 的 shell 命令、对齐条目确认、限额暂停的恢复）出现在所有侧栏的审批队列里，用户在任意一个侧栏上批，批完其他侧栏同步消失。

## 3. 架构

```
各家侧栏（薄渲染层，只负责画和把按钮操作转成请求）
  Claude mod 侧栏 ── dsh 插件抽屉 ── OpenCode（视实测结果）
          │ 127.0.0.1 HTTP：/v1/view（视图模型，长轮询或 SSE）、/v1/act（操作）、/v1/join
          ▼
hub（Windows 原生 Python 后台进程，每个房间一个；不依附于任何一个侧栏或会话）
```

- **hub 独立于侧栏**：主控会话被关掉，房间照常运行；任何成员的侧栏都可以接着管理。"主控"只表示房间是在哪里开的，以及默认由谁当协调者，不是单点。主控可以在侧栏里移交给另一个成员。
- **hub 怎么启动**：开房间时由主控的插件拉起；之后任何一家侧栏连不上 hub 时，都可以把它再拉起来（同一房间只允许一个 hub 进程，用锁文件保证）。不需要常驻窗口，也不需要开机自启。
- **三家共用一个视图模型**：hub 提供结构化的 `/v1/view`（成员、时间线、对齐条目、审批队列、预设运行状态），每家侧栏只是用自己的界面元素把它画出来。功能和规则都在 hub，侧栏里不写业务逻辑，这样三家的行为一致，新增功能只改 hub 和各家的渲染。
- **命令行保留**：`xmuse` CLI 继续用于脚本、实验和排错，和侧栏走同一套接口。

## 4. 各家侧栏

### 4.1 Claude（桌面版 Code 标签和 Code CLI）——用 mod

依据：本机 Claude Code 2.1.295 的 mod 接口（插件函数钩子）。接口是早期版本，会随版本变化，以类型声明文件为准。

| 需要的能力 | mod 里的做法 |
|---|---|
| 侧栏 | `$.ui.open({ id, title })` 打开面板，`ui.render` 钩子在 `{ component: 'Pane' }` 上画；只能用宿主提供的元素（Box、Text、Button、Markdown、Input、Select……），不能嵌网页 |
| 输入框上方横幅 | `{ component: 'AbovePrompt' }`：未处理的 @、待审批数 |
| 提示 | `$.ui.toast`、`$.ui.status`、`$.ui.notify` |
| 访问 hub | `$.http.fetch("http://127.0.0.1:<端口>/...")`（组织的网络策略可能拦截，需实测） |
| 刷新 | `session.start` 里起 `$.clock.every` 长轮询 `/v1/view` |
| 推送唤醒 | `$.prompt.submit({ text })`：会话空闲时起一个新回合，模型读到"xmuse 插件发来一条消息"。**不用** `asUser` |
| 回合进行中的提示 | `$.session.append`（用户角色、`isMeta`），只用于"有新的 @"这类提示 |
| 命令 | `$.command.register({ name: 'xmuse' })`：`room new`、`invite`、`join <码>`、`status`、`leave` |
| 安装 | 用户在终端执行 `/plugin install xmuse --marketplace <owner>/<repo>`（用户级，桌面版 Code 标签的本地会话也会加载）；开发期用 `CLAUDE_CODE_PLUGIN_DIRS` |

需要实测：桌面版 Code 标签里侧栏的停靠和宽度；`$.http.fetch` 到 127.0.0.1 是否放行；`$.prompt.submit` 在桌面版里起回合的表现；mod 拿到的会话 id 能否和 hub 记录的对上；侧栏里 Input、Select 在桌面版的表现（开房间、邀请要用）。

### 4.2 dsh

- 绑定和投递：现有插件包的中继（`/xmuse bind`）改成邀请码形式 `/xmuse join <码>`；长轮询和"按会话强制身份"已经有了。
- 侧栏：插件包加前端部分（dsh 插件可以往网页界面注入脚本，本机 dsh-pixel-maid 就是这样做的），画一个可以收起的抽屉。数据走插件宿主侧的同源路由转发 hub，令牌只在宿主进程里，不进浏览器。
- hub 改为 Windows 原生后，dsh 不再需要 WSL 互操作，`wsl.exe` 参数转义、UNC 路径写入、沙箱拒绝 WSL 这几类问题一并消失。

### 4.3 OpenCode

- 唤醒和投递：沿用现在的做法，每个实例一个 `opencode serve`，hub 用它的 prompt API 加 SSE。
- **待实测**：用户在 OpenCode TUI 或桌面版里打开的会话能否连到 hub 启动的 serve 实例，从而在用户正在看的界面里看到投递的消息；插件能否注册命令、能否加侧栏。
- 如果 OpenCode 做不了侧栏：它仍然可以是房间成员（被邀请、收发消息、toast 提示），但**不能当主控**，房间信息和审批由其他成员的侧栏承担。

## 5. 功能分层

三家侧栏的界面能力不一样，按层次保证一致：

| 层次 | 内容 | 要求 |
|---|---|---|
| 基本 | 成员和在线状态、时间线（按话题分组、@ 高亮、只看 @ 我）、发消息、审批队列 | 每个有侧栏的 provider 都必须有 |
| 管理 | 开房间、邀请、移出成员、移交主控、暂停和恢复 agent | 每个有侧栏的 provider 都必须有 |
| 详情 | 对齐条目和替换关系、预设运行（阶段、倒计时、快照、冲突和越界事件）、token 用量 | 尽量都有；界面元素不够的一家可以只显示摘要 |
| 以后 | 记忆（MemoryOS）查看、编辑、撤销 | 另起设计稿 |

## 6. 邀请和绑定协议

| 步骤 | 内容 |
|---|---|
| 开房间 | 侧栏调用 `/v1/rooms {dir, name, vendor, session_id}`（hub 不在时插件先拉起 hub）→ 创建房间，调用者成为第一个成员和主控 |
| 创建邀请 | `/v1/act invite {vendor, role, name?}` → `{code, expires_at}`；任何成员的侧栏都能发起（用户操作） |
| join | `/v1/join {code, vendor, session_id, client_info}` → hub 校验码、vendor 匹配、没过期没用过 → 创建成员，返回成员令牌 |
| 令牌存放 | 只给插件进程，**不进模型上下文**，不写进工作区 |
| 身份强制 | 绑定后这个成员的所有调用都要带 `x-xmuse-session`，和绑定的会话不一致就拒绝（dsh 现在的做法推广到三家） |
| 换会话 | 同一成员可以用新邀请码重新 join 到别的会话，后一次生效，hub 记一条通知 |
| 离开 | `leave` 或侧栏上"移出"：解绑，未投递的消息保留 |

## 7. 安全模型

审批和管理放进所有侧栏之后，关键在于区分"用户在侧栏上点的"和"agent 自己发起的"。

| 风险 | 处理 |
|---|---|
| agent 自己批准自己的请求 | 侧栏按钮只有人点得到：模型没有工具去按自己侧栏上的按钮（开了 computer use 的除外，见下一行）。侧栏发出的操作请求带一个**操作令牌**，只在插件进程里，模型的工具调用拿不到；agent 的工具调用只能用成员令牌，hub 拒绝成员令牌做审批和管理 |
| 开了 computer use 的 agent 能操作整个桌面 | 高风险操作（批准白名单外的 shell 命令、`always` 类审批、移出成员、移交主控）由 **hub 自己弹出 Windows Hello**（`UserConsentVerifier`），需要人本身在场；和用户在哪个侧栏上点的无关 |
| 同一 OS 用户能读插件存放的令牌 | 已知缺口（agent 单独 OS 用户已搁置）。令牌改存 Windows 凭据管理器（DPAPI）能挡住"顺手读文件"，挡不住有意的同用户进程；高风险操作仍有 Windows Hello 兜底 |
| 消息来源 | 侧栏发出的消息记为"用户（经 Claude 侧栏 / dsh 侧栏 / OpenCode 侧栏）"；mod 唤醒 Claude 时不用 `asUser`，模型读到的是"xmuse 插件发来的消息"，正文写明原始发送者 |
| 网络 | hub 只监听 127.0.0.1 |

## 8. hub 迁到 Windows 原生要改什么

- 路径和状态目录：`%LOCALAPPDATA%\xmuse\<房间>-<hash>\`；去掉所有 `wsl.exe`、UNC 路径、`to_win` 一类的转换。
- 启动各家：直接启动 `claude.exe`、`opencode.exe`、dsh 的 `cli.js`。
- 进程管理：POSIX 信号、`setsid`、进程树判断要换成 Windows 的做法（Job Object、父进程链）。审批改由侧栏加操作令牌承担后，"调用来自用户自己的终端（有控制终端）"这条判断可以退役，CLI 的审批改为同样走操作令牌（CLI 由用户自己运行，令牌从凭据管理器取）。
- 测试：现在的 337 个测试在 Linux 上跑。加 Windows CI（GitHub Actions windows-latest），依赖 pty 的测试改写或标记为只在 POSIX 跑。
- 分发：一个安装程序（或 `xmuse setup`）装好 hub（PyInstaller 或嵌入式 Python），并把三家的插件注册好。它只是安装程序，装完就退出。
- T15 实验仍在 WSL 里的 hub 上跑，迁移在独立分支上做，不影响实验。
