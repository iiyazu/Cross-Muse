# 编排预设 plan-split-integrate 与团队实验设计（2026-10-11，r7 规划）

> 用途有两个：一是实验里的"团队组"，二是产品里的编排预设 `xmuse run --preset plan-split-integrate`。本文定拓扑、阶段、信息层的用法、护栏、测量和实验分组；实现任务见交接文档 §10（T12–T15）。

## 1. 为什么是这个拓扑

T6 和审计的结论是：在只需要一个人写代码的任务上，对齐层的作用测不出来，因为那类任务没有协调的需求。只有当**多个执行者并行修改同一个系统**、必须共享接口约定、数据格式和各自查到的事实时，信息层才有事可做。所以团队的形式是：一个规划者读题、拆分、定约定，两个执行者并行实现，规划者负责集成。

## 2. 角色与实例（10-11 用户定）

| 角色 | 实例 | 外壳 / 模型 | 写权限 |
|---|---|---|---|
| 规划者 P | `dsh-ms13` | dsh / opencode-go/muse-spark-1.3-contributor | 主分支上只修合并冲突和接线，**不写功能代码** |
| 执行者 E1 | `oc-ms13` | opencode / muse-spark-1.3-contributor | 自己的 worktree，只改归属自己的文件 |
| 执行者 E2 | `dsh-fl` | dsh / DeepSeek V4.1 Flash，走 opencode-go 渠道（确切的模型 id 由 base 用 `opencode models` 或 dsh 的 overlay 核实后写进 meta） | 同上 |

E1 与 P 是同模型、不同外壳；E2 与 P 是同外壳、不同模型。三个实例的模型都走 opencode-go 渠道，所以模型差别不会混进渠道差别。注意：T6 的 r7 臂用的是 `deepseek-official/deepseek-v4-flash`，和这里不是同一个版本、也不是同一个渠道，两者的结果不能直接合并。三个实例在同一个工作区注册，需要 T12。

## 3. 阶段（hub 推进的状态机）

| 阶段 | 谁 | 做什么 | 上限 | 结束条件 / 产物 |
|---|---|---|---|---|
| P0 规划 | P | 读题面和代码，产出：任务拆分（按模块或文件，写明**文件归属**）、模块间约定、验收清单 | 10 分钟 | 约定登记为 decision 或 convention；任务以 handoff 下发，生成 assignment（assignee 和 depends_on）；验收清单写进计划消息 |
| P1 并行执行 | E1、E2 | 在各自的 worktree 里实现；随时登记发现（assumption）和疑问（question）；被依赖的条目还没解决时，hub 不唤醒对应的 assignment | 25 分钟 | 各自调用 `xmuse_done(stage="part")`，填好交接字段 → 存快照 S-E1、S-E2 |
| P1 期间 | P | 有新的 question 指向 P 时被唤醒，答完后回去待命；答复登记为 decision，替代原来的 assumption | — | — |
| P2 集成 | P | 合并两个分支 → 存快照 S-int → 跑全套检查和验收清单 | 10 分钟 | 集成报告：哪些通过、哪些失败、各归谁 |
| P3 定向修复 | 对应的执行者 | P 把失败项指派给负责那部分的执行者，修完再集成 | 每轮 8 分钟，最多 2 轮 | 快照 S-fix-k |
| 收尾 | hub | 快照 F → 官方评测 | — | — |

- 全局上限 60 分钟，与单干组相同。任何阶段超时，hub 都强制推进到下一阶段，并记一条事件。
- 执行者要改不归自己的文件，必须先发 question 向 P 申请；hub 检测到越界修改就记一条违规（只记，不拦）。

## 4. 信息层的具体用法（T-xmuse 组）

| 协作问题 | 机制（现有 → 需补的部分见 T14） |
|---|---|
| 约定（接口、数据格式、命名） | P 用 `kind=decision`（或 convention）登记，scope 写成 `module:<名字>` 或 `all`；每次唤醒时 hub 按 scope 注入（wakepack），不依赖聊天记录，也不怕上下文压缩 |
| 发现（影响别人的事实） | 执行者用 `kind=assumption` 登记并写明 scope；hub 只注入给 scope 命中的 agent；P 确认后用 decision 替代（supersedes） |
| 疑问 | `kind=question`，hub 唤醒 P；P 的答复成为 decision，并按 scope 传播 |
| 依赖 | handoff 生成的 assignment 带 depends_on；依赖没解决之前不派活，**依赖一解决就唤醒 assignee**（T14 需要核实或补齐） |
| 交接 | `xmuse_done` 的交接字段：做了什么、为什么、还剩什么、验证证据；P 集成时逐项对照 |

## 5. 实验分组（每题每组 3 次）

| 组 | 拓扑 | 信息层 |
|---|---|---|
| S-best | T11a 等单干探针里最强的实例单干 | — |
| **T-xmuse** | P + E1 + E2 | 全开（第 4 节） |
| **T-plain** | 同一组人、同样的阶段和时限 | 关闭：P0 的计划以一条普通消息下发；之后只能发 `kind=message`；没有 decision、assumption、question 的登记和注入，没有 scope 路由，也没有依赖唤醒 |
| T-silent（可选） | 同上 | 计划下发之后禁止通信（下限） |

- **T-xmuse 对 T-plain**：唯一的变量是信息层。这是 xmuse 的核心论点。
- **T-xmuse 对 S-best**：团队整体值不值。

## 6. 测量

结果指标：
- 整题通过；
- 部分得分：隐藏测试通过数 / 总数，自建 bug 猎场用修好的 bug 数 / 总数；
- 自以为完成但没通过的比例。
- S-E1、S-E2、S-int、S-fix-k、F 每个快照都单独评测，能看出每个阶段的净变化。

信息层专属指标：
- **集成缺陷**：两个执行者各自的自测都通过、合并后才失败的问题数；
- **约定违背**：合并后的代码与已登记 decision 不一致的次数（用大模型逐条对照，再人工抽查）；
- **矛盾事实**：两方对同一件事给出不同说法的次数；
- **返工**：集成之后为了对齐而改动的行数；
- **等待**：question 从提出到答复的延迟，以及执行者空等的总时长；
- **上下文效率**：注入的字节数，对比 T-plain 里读聊天记录的字节数；
- 合并冲突数，越界修改数。

成本指标：每个角色、每个阶段的 token、时间和消息条数。

## 7. 题目

- **主实验**：自建"屎山 bug 猎场"（T15）。一个 3 万–6 万行的开源代码库，30–60 个分布在不同模块的真实回归 bug，每个 bug 由它的修复提交里的测试判定。天然可以按模块拆分，跨模块的 bug 和共用的格式正好考验信息层。
- **流程跑通**：在 T15 就绪之前，先用 Legacy-Bench 里多模块的题（以 T11a 的结果为准）跑通整个流程。这类题偏小，拆分的协调成本可能比收益高，只用来验证流程，不作为主要结论。

## 8. 无人值守的护栏

- 每个阶段都有时间上限并强制推进；定向修复最多 2 轮；保留原有的唤醒链上限 MAX_CHAIN_WAKES。
- agent 崩溃重试一次，再失败就降级（由另一名执行者接手，或者跳过这部分），并记录下来。
- 所有命令都在一次性容器里执行，沿用实验专用的审批策略，不需要人介入。
- P 没有在 P0 的时限内交出计划时，记为失败 run，不改由 hub 代为拆分。
