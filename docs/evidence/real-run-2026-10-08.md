# 真实运行案例：一个需求从提出到集成（2026-10-08）

这一页记录 xmuse 第一次在**产品路径**上用真实 agent 端到端交付需求的过程：哪里卡住了、怎么诊断、怎么修，修完后复测的数据。房间里干活的是 OpenCode（lead 和 owner）和 Antigravity/agy（跨家族复核人），**不经过 Claude**。人通过 Claude Code 插件 `/xmuse` 操作。

**需求**（三轮相同）：给 `ledger` 报表加一个折扣行 `discount_line(subtotal, rate)`，输出形如 `"Discount: -2.00"`，并补测试。种子仓库是一个小型 Python 项目，门禁是 `python-uv/v1`：diff 检查、ruff、mypy、pytest。

## 目标流程

```text
人提需求 → lead 在看板提出拆分（模块、路径、契约、验收）→ 人批准（摘要防护）
→ owner 认领并在自己的克隆里实现 → owner 报 done（只是声明）
→ 主机按门禁验证（失败则打回返工）→ 跨家族 agent 复核 → accepted → 主机集成
```

`done` 只是 agent 的声明，`accepted` 才算完成。验证、复核、集成是三条独立的轴。

## 第一轮（P1 首跑）：能走通，但处处是坑

| 现象 | 根因 | 修复 |
|---|---|---|
| 托管启动直接失败 | Runner 的 MCP 就绪探测要求"恰好 1 个工具"，而 MCP 从 #423 起已经暴露 8 个工具。**这条启动路径自 #423 起一直是坏的**，测试没覆盖到 | #465：探测改为与服务端发布的工具集合精确比对；CI 里用真实 MCP 进程测试 |
| 沙箱里的 agent 写临时文件报只读（EROFS） | bwrap 沙箱继承了宿主的 `TMPDIR`，而它指向 `$HOME` 下的只读挂载 | #466：三类沙箱统一把 `TMPDIR/TMP/TEMP` 固定到沙箱私有的 `/tmp` |
| `uv run` 下 agy 报找不到 python3 | `uv` 把 `$HOME` 下的 venv 放在 PATH 最前面，沙箱看不到它 | #466：沿 PATH 找第一个不在 `$HOME` 下的 python3 |
| agy 复核连续 3 次超时（每次 420 s），转人工复核 | 当时以为是 agy 太慢，记为观察项 | 见第三轮 |

## 第二轮（root2）：自然需求没有进入看板

**现象**：人只用自然语言提需求（不提看板）时，lead 直接用消息把任务交接给 owner，**完全绕过了拆分、验证和复核**。

**修复**（#467）：在有可写 owner 的房间里，给 lead 和 owner 加上"先上看板"的指引。按项目不变量，平台不能替 agent 做决定，所以这一轮只改指引，不加服务端规则。

**复跑**：lead 自己提出了拆分并附上契约；owner 通过看板报 done；第一次验证被 ruff（`I001` import 排序）打回，owner 修好后通过，主机完成集成。

## 第三轮（root3）：复核超时的真正原因，以及指引不够稳

### 复核超时不是因为慢

逐步读了 agy 那三次复核的完整记录（153 步）：
- agy 在第 1 分钟就开始提交复核结论，**一共提交了约 60 次，全部被拒**。它在猜 `verdict` 的取值：依次试了 `test`、`approve`、`approved`、`clean`、`validate`、`approve_module`……
- 原因一：agy 通过一个通用包装调用 MCP 工具，**看不到工具的参数定义**，只能从报错里学。服务端对"缺参数、多参数"会列出参数名，但对取值不合法只回一个错误码 `room_board_review_verdict_invalid`，不说合法值是 `endorse` 和 `object`。
- 原因二（更严重）：复核指令让复核人用 `chat_room_board_read` 带上 `review_id` 读 diff，服务层也支持这个参数，**但 MCP 工具定义漏写了它**（自 #431 起），入口直接按"未知参数"拒掉。也就是说，**从 #431 以后，所有 agent 复核人都读不到要复核的代码**。

**修复**（#470）：工具定义补上 `review_id`；MCP 入口校验取值范围，不合法时直接列出合法值；新增结构性测试，逐个比对工具定义和服务方法的参数，以后再漏写会直接失败。

### 指引不够稳

**现象**：同样的指引、同样的模型，这一次 lead 把拆分**写成了一段文字**作为普通提议提交，没有调用看板工具。看板上什么都没有，房间空等了约 1 小时。

**修复**（#471）：在有 owner 的房间里，lead 用文字提交拆分会被服务端拒绝，报错提示改用 `chat_room_board_propose_split`。这是校验，不是替 agent 决策，思路与已有的"复核人不给结论就不能结束这一轮"一致。

### 复跑结果（root3，修复 #470 后）

| 时间（JST） | 事件 |
|---|---|
| 20:26 | lead 用看板工具提交拆分（1 个模块 `ledger-discount`，附契约 `discount-line-api`） |
| 20:49 | 人批准拆分（输入摘要前 6 位 `d5b853` 防护） |
| 20:49–20:51 | owner 认领、实现、报 done，用时 116 s |
| 20:51:37 | 验证失败：ruff `I001`，打回返工 |
| 20:52:09 | owner 修好后 22 s 再报 done，**验证通过** |
| 20:52:26 | agy 收到复核请求 |
| 20:53:12 | agy 带 `review_id` 调用 `chat_room_board_read`，读到 diff |
| 20:54:18 | agy 的**第一次正式提交就成功**：`verdict: endorse`（20:53:52 发出） |
| 20:54:19 | 自动接受、自动集成 |

**复核耗时：修复前 3 次各 420 s 超时后转人工 → 修复后 1 分 52 秒自动通过。** 复核人的超时设置没有改动，也不需要改。

### 复跑中又发现的问题（已修）

- agy 把顶层参数 `reply_to_activity_id` 放进了 `outcome_payload`，报错只有错误码。修复（#472）：嵌套对象里出现不允许的字段时，报错写出字段名、位置和允许的字段；如果这个字段本该放在顶层，会直接说明。
- 插件授权 1 小时过期后，人重新配对，但新授权没有覆盖原来的房间，面板仍显示"已授权"却没有任何按钮。修复（#472）：面板明确显示"不含当前房间"，并给出 `pair --room <完整 id>`。
- 投递失败（`exhausted`）之后，即使 agent 已经正常完成了新的工作，状态仍然一直显示"尝试已耗尽"。修复（#473）：状态改为跟随失败之后的最新结果，失败那条投递和它的重试入口保留。

## 得到的结论

1. **给 agent 的报错要说清楚该怎么做。** 看不到工具定义的 agent 只能从报错里学，一个只有错误码的报错，就能让它原地打转 7 分钟。
2. **该强制的约束，不要只写在指引里。** 同样的指引，这一轮遵守，下一轮不遵守；协议层面的校验才稳定。
3. **只有真实运行才会暴露的问题，测试覆盖不到。** 这一天修的 7 个 PR 里，#465 和 #470 都是潜伏了好几天的问题，测试一直绿着。
4. **先读完整记录再下结论。** 复核超时最初被当成"agy 太慢"，差点通过调大超时来"解决"。

## 局限

- 三轮都是单模块的小任务；多模块、有依赖、长时间运行的房间还没有跑过。
- r7 的外网不稳定，约 41% 的 agy 会话遇到过网络错误；本页的计时都是网络正常时的结果。
- 第三轮复跑用的代码版本是 `0d452b2`（包含 #470，不含 #471–#473）；#471–#473 的效果由测试验证，还没有在真实运行里复测。
