# 记忆证据：MemoryOS 什么时候有用，什么时候没用

xmuse 的记忆来自姊妹项目 [MemryOS-lite](https://github.com/iiyazu/MemryOS-lite)：一个评测驱动、**来源可追溯**的 agent 记忆服务。它的核心是一个无状态的 `/curate` 接口，用 LangGraph 实现，把模块的活动历史整理成一份"续命包"（pack）：现行决定、接口契约，以及错题本（教训和重复次数）。xmuse 通过 HTTP 调用它，开关是 `XMUSE_MODULE_MEMORY`，**目前默认关闭**。产品路径上的证据（第 4 节）支持"经审批的规则能让别家的 agent 对齐"，但样本还小，所以暂时不改默认值。

下文的数字来自评测记录（FINDINGS §9.17–§9.23，2026-10-03 至 10-04）。评测框架和数据集都在 MemryOS-lite 仓库里（`memoryos eval modulemem`，数据在 `benchmarks/modulemem/`）。

## 1. 历史超出上下文预算时，续命包以约 1/6 的 token 接近全量历史（§9.19）

长模块：约 6.2k token 的活动历史，预算 1500 token。

| 组 | 答对 | 缺失 | 证据 token |
|---|---|---|---|
| **pack**（整理后的续命包） | **0.95** | 0.00 | 1075 |
| full_history（全量历史，作为上限） | 0.97 | 0.00 | 6160 |
| raw_log（同预算下最近的原始日志） | 0.31 | 0.61 | 1472 |
| recent（最近几条） | 0.06 | 0.91 | 226 |

原始日志的失分主要是**缺失**：早期的决定被预算截掉了。

## 2. 行为层面：重启后的模块负责人是否还遵守决定和契约（§9.20）

被测者只能看到"任务描述 + 该组提供的记忆"，据此写出代码改动；评委逐条判定 99 条要求（每组 2 遍、64 个任务）。

| 组 | 全部满足 | 违反率 | 任务全满足 | 证据 token |
|---|---|---|---|---|
| none（不给记忆） | 0.10 | 0.62 | 0.00 | 0 |
| raw_log | 0.57 | 0.35 | 0.20 | 1430 |
| **pack** | **0.92** | **0.06** | **0.78** | 972 |
| full_history | 0.92 | 0.03 | 0.80 | 6120 |

pack 与全量历史持平，token 只用了约 1/6。人工抽查评委标签，约 80% 一致；误判两个方向都有，并且主要落在 none 和 raw_log 组，会**缩小**而不是放大 pack 的领先。

## 3. 真实仓库、真实编码 agent：不重犯旧错（§9.22–§9.23）

一旦有了代码库，记忆的边际价值就小了很多，这是这组实验最重要的发现。

**设置**：4 个种子仓库（orders、crm-sync、invoices、checkout），每个都按历史手工加入技术债，共 11 处。例如一个旧的导出接口仍然逐单查询（N+1），或者配置默认值仍是历史上已经废弃的 500。OpenCode 在 bwrap 沙箱里真正改代码，每组 30 个任务 × 2 遍，3 组共 180 次运行。

| 组 | 要求满足 | 违反 / 被触及 | **复用技术债的任务** |
|---|---|---|---|
| none | 0.73 | 0.11 | **10/60** |
| raw_log | 0.73 | 0.08 | **3/60** |
| **pack** | **0.82** | **0.04** | **0/60** |

- 技术债复用是确定性指标（只扫新增行），每一条都人工核对过。none 的 10 次全是真复用；pack 不但 0 次，还在 3 个任务里**主动把债还了**。
- 对照第 2 节：不给记忆时，满足率从约 0.10（只写代码改动、看不到仓库）升到 0.73（能读仓库）。**现行的决定大多已经写在代码里了**，记忆的增量缩小到约 +0.09。

**由此修正的价值主张**：记忆的主要作用，是**防止 agent 被代码里看似可用的旧东西带偏**，而不是"补上代码里没有的一切"。

## 负面结果（同样重要）

- **短模块、预算装得下原文时，原始日志不差于续命包**（§9.17、§9.19 预算扫描）：预算 1000 以上时，raw_log 反超；pack 只在小预算（≤600）下赢在教训题。
- **跨房间问答上，整理后的记忆与项目级原始检索在噪声范围内**（§9.9、§9.15），优势只在证据体积和审批治理。
- "已取代降权"机制在理想标记下有效（陷阱题旧值率 0.06 → 0），但**真实 curator 在新旧值落在同一窗口时不会产生取代标记**，这是标记机制的设计问题，记录在案，暂不处理（§9.19）。
- 一次被误读的"过度合并"，逐条核对后发现是**标准答案漏标**，修正后 pair precision 0.77 → 0.96（§9.19）。

## 4. 产品路径上的评测（effective-tests E1–E3，2026-10-07 至 10-08）

前面几节的实验都在 MemoryOS 自己的评测框架里做。这一组把记忆接进 xmuse 的**真实房间**：历史经产品 worker 落库，记忆由产品的 curate 路径整理，被测 agent 在种子仓库里真正写代码。**注入方式是跑前冻结的静态快照，不是运行时的实时召回**：每一臂的记忆在开跑前渲染成固定文本交给 agent，实验过程中召回调用次数为 0。所以这一组测的是"整理出来的记忆交给 agent 以后，有没有用"，没有测实时召回链路。设计在看数据之前就冻结了，包括判读矩阵；每个实验都有四道门：泄漏防火墙（答案不得出现在种子、git log 和题面里）、提炼检查、余量校准、同 token 预算（原始召回和整理后的记忆都锁在 800 token 以内）。

| 实验 | 问题 | 结果（只计有效格） | 按预注册矩阵的读法 |
|---|---|---|---|
| **E3 跨 agent 规则对齐** | Room A 经人审批的项目规则，Room B 里另一家的 agent（agy）会不会照做？没审批的会不会泄漏过去？ | 照做：不开记忆 0/3、**已审批 3/3**、未审批 0/2、标准答案 3/3；未审批规则的原文没有出现在被测 agent 的上下文和回执里 | **经审批的规则能让另一家的 agent 对齐**：已审批比未审批多 +2，比不开记忆多 +3。注意：未审批这一臂在实现上与不开记忆静态等价，**没有测到运行时召回门禁的拦截**，所以不据此宣称"门禁挡住了泄漏" |
| **E2 遗忘 + 版本** | 事实早已滑出近期窗口、中途还改过值时，agent 用的是现值、旧值，还是编造的值？ | 现值：原始召回 2/4、**整理后的记忆 6/6**、标准答案 4/4、全量历史 8/8；用到旧值的次数全部为 0 | 在两臂都有效的任务上，整理后的记忆比同预算的原始召回多 +2，**方向上占优** |
| **E1 任意性事实** | 交接后，新 owner 能不能用对推导不出来的项目事实（如商户号）？ | 只有 1 个有效任务：不开记忆、原始召回、整理后的记忆都是 0/2，标准答案 2/2 | **没有测出增益。** 记忆已经送达，但 agent 读了没照做：它把这些值写成了参数，测试里用了示例值 |

另外有两个发现：
- **agent 会有理由地拒做**（E2 中 9 个作废格里有 6 个）：它认为"派生出来的记忆或不可信的召回，不能推翻章程、契约和代码体例"。这对记忆的产品设计是个约束：记忆要能被 agent 当作权威，就必须带来源，而且经过审批。E3 的结果正好与此一致。
- E1 有两个任务因量具失效作废：连标准答案组都是 0 分，说明"把值逐字写进 diff"这个度量和"好的工程做法是参数化"相冲突。按规则，这两个任务不进入配对。

**结论**：在产品路径上，最清楚的价值是**经审批的规则让跨厂家的 agent 对齐**（E3）；版本和遗忘有方向性证据（E2）；任意性事实的交接没有测出增益（E1）。三个实验每个有效格都只有 1 次运行，**样本很小，不做显著性宣称**。

**实时召回链路的现状**：房间级的归档召回在发布验证里实跑过。v0.4.0 的三房间记忆多样性运行得到 6 个非空、可追溯出处的召回回执，19 条出处在 `chat.db` 里重新证明；v0.3.1 证明过跨房间召回到一条经审批的项目规则（见 README 的发布验证一节和 `docs/releases/v0.4.0.md`）。这些运行验证的是"能召回、出处可证"，**没有测 agent 的行为因此改变**。模块记忆（续命包，`XMUSE_MODULE_MEMORY`）在真实交付中实时召回并影响行为，目前还没有演示过，计划在下一次带记忆的真实运行中补上。

## 局限

- 回答模型、评委、curator 都是同一家族（muse-spark-1.3），盲化和人工抽查只能缓解。
- 数据集由 LLM 起草、规则校验；种子仓库的技术债由评测设计者手写。虽然每处都有历史依据，但真实仓库里的技术债未必这么容易被记忆识别。
- 每格 2 到 3 遍，遍与遍之间的波动不小（例如 raw_log 含违反的任务，两遍分别是 9/30 和 3/30）。
- 技术债正则是看过结果之后才收紧的；它只影响 pack 组的计数（4 → 0），而且每一条都人工核实过。
- 第 4 节：每格只跑 1 次；有效格少，作废格多（E2 有 9 格作废）；E3 的冲突任务没有触发（冲突规则在提炼阶段就被正确排除了，所以没有可测的对象），房间历史也短（A 18 条、C 4 条）；E2 的人工验收还在排期；被测 agent 的网络不稳定，E3 有 1 格因认证错误（401）作废；E3 与同机的另一次真实运行有部分时间重叠，两边的 agy 共用一个工具定义缓存目录；记忆以跑前静态快照注入，不经过实时召回，所以召回时的审批门禁和召回质量都不在测量范围内。
