# 记忆证据：MemoryOS 什么时候有用，什么时候没用

xmuse 的记忆来自姊妹项目 [MemryOS-lite](https://github.com/iiyazu/MemryOS-lite)：一个评测驱动、**来源可追溯**的 agent 记忆服务。它的核心是一个无状态的 `/curate` 接口，用 LangGraph 实现，把模块的活动历史整理成一份"续命包"（pack）：现行决定、接口契约，以及错题本（教训和重复次数）。xmuse 通过 HTTP 调用它，开关是 `XMUSE_MODULE_MEMORY`，**目前默认关闭**。默认关闭的原因是：在产品路径上它值不值得开，证据还在收集中（见第 4 节）。

下文的数字来自评测记录（FINDINGS §9.17–§9.23，2026-10-03 至 10-04）。评测框架和数据集都在 MemryOS-lite 仓库里（`memoryos eval modulemem`，数据在 `benchmarks/modulemem/`）。

## 1. 历史超出上下文预算时，续命包以约 1/6 的 token 接近全量历史（§9.19）

长模块：约 6.2k token 的活动历史，预算 1500 token。

| 组 | 答对 | 缺失 | 证据 token |
|---|---|---|---|
| **pack**（整理后的续命包） | **0.95** | 0.00 | 1075 |
| full_history（全量历史，作为上限） | 0.97 | 0.00 | 6160 |
| raw_log（同预算下最近的原始日志） | 0.31 | 0.61 | 1472 |
| recent（最近几条） | 0.06 | 0.91 | 226 |

原始日志的失分主要是**缺失**：早期的决定被预算截掉了。

## 2. 行为层面：重启后的模块负责人是否还遵守决定和契约（§9.20）

被测者只能看到"任务描述 + 该组提供的记忆"，据此写出代码改动；评委逐条判定 99 条要求（每组 2 遍、64 个任务）。

| 组 | 全部满足 | 违反率 | 任务全满足 | 证据 token |
|---|---|---|---|---|
| none（不给记忆） | 0.10 | 0.62 | 0.00 | 0 |
| raw_log | 0.57 | 0.35 | 0.20 | 1430 |
| **pack** | **0.92** | **0.06** | **0.78** | 972 |
| full_history | 0.92 | 0.03 | 0.80 | 6120 |

pack 与全量历史持平，token 只用了约 1/6。人工抽查评委标签，约 80% 一致；误判两个方向都有，并且主要落在 none 和 raw_log 组，会**缩小**而不是放大 pack 的领先。

## 3. 真实仓库、真实编码 agent：不重犯旧错（§9.22–§9.23）

一旦有了代码库，记忆的边际价值就小了很多，这是这组实验最重要的发现。

**设置**：4 个种子仓库（orders、crm-sync、invoices、checkout），每个都按历史手工加入技术债，共 11 处。例如一个旧的导出接口仍然逐单查询（N+1），或者配置默认值仍是历史上已经废弃的 500。OpenCode 在 bwrap 沙箱里真正改代码，每组 30 个任务 × 2 遍，3 组共 180 次运行。

| 组 | 要求满足 | 违反 / 被触及 | **复用技术债的任务** |
|---|---|---|---|
| none | 0.73 | 0.11 | **10/60** |
| raw_log | 0.73 | 0.08 | **3/60** |
| **pack** | **0.82** | **0.04** | **0/60** |

- 技术债复用是确定性指标（只扫新增行），每一条都人工核对过。none 的 10 次全是真复用；pack 不但 0 次，还在 3 个任务里**主动把债还了**。
- 对照第 2 节：不给记忆时，满足率从约 0.10（只写代码改动、看不到仓库）升到 0.73（能读仓库）。**现行的决定大多已经写在代码里了**，记忆的增量缩小到约 +0.09。

**由此修正的价值主张**：记忆的主要作用，是**防止 agent 被代码里看似可用的旧东西带偏**，而不是"补上代码里没有的一切"。

## 负面结果（同样重要）

- **短模块、预算装得下原文时，原始日志不差于续命包**（§9.17、§9.19 预算扫描）：预算 1000 以上时，raw_log 反超；pack 只在小预算（≤600）下赢在教训题。
- **跨房间问答上，整理后的记忆与项目级原始检索在噪声范围内**（§9.9、§9.15），优势只在证据体积和审批治理。
- "已取代降权"机制在理想标记下有效（陷阱题旧值率 0.06 → 0），但**真实 curator 在新旧值落在同一窗口时不会产生取代标记**，这是标记机制的设计问题，记录在案，暂不处理（§9.19）。
- 一次被误读的"过度合并"，逐条核对后发现是**标准答案漏标**，修正后 pair precision 0.77 → 0.96（§9.19）。

## 4. 产品路径上的评测（进行中）

上面的实验都是在 MemoryOS 自己的评测框架里做的。把记忆接进 xmuse 的真实房间、在产品路径上做成对对照（不给记忆 / 原始记录 / 整理后的记忆 / 标准答案）的评测正在进行，结果出来后补到这里。

## 局限

- 回答模型、评委、curator 都是同一家族（muse-spark-1.3），盲化和人工抽查只能缓解。
- 数据集由 LLM 起草、规则校验；种子仓库的技术债由评测设计者手写。虽然每处都有历史依据，但真实仓库里的技术债未必这么容易被记忆识别。
- 每格 2 到 3 遍，遍与遍之间的波动不小（例如 raw_log 含违反的任务，两遍分别是 9/30 和 3/30）。
- 技术债正则是看过结果之后才收紧的；它只影响 pack 组的计数（4 → 0），而且每一条都人工核实过。
